## 1. 风险管理方法

### 1.1 闭环流程

| 环节 | 动作 | 频次 | 输出 |
|---|---|---|---|
| 识别 | 按六个类别（技术/进度/合规/环境/范围/质量）逐项排查；每阶段门禁前补一轮 | 阶段初 + 门禁前 | 风险登记册新增条目 |
| 评估 | 判定概率与影响，计算风险值，标注是否落入「高」区（值 ≥ 6） | 随识别同步 | 风险值与优先级 |
| 应对 | 从规避/转移/减轻/接受四策略中选一，写明具体动作、责任人、触发点 | 随评估同步 | 应对措施列 |
| 监控 | 门禁复核风险状态（关闭/降级/升级），偏差 > 1 周触发再评估 | 每阶段 1 次 | 风险状态变更记录 |
| 复盘 | 阶段结束时记录「哪些风险发生了、措施是否有效」 | 每阶段末 | 门禁记录中的风险小节 |

### 1.2 评估准则

| 维度 | 高（3） | 中（2） | 低（1） |
|---|---|---|---|
| 概率 | 经验上必然发生或已出现征兆 | 有可能，取决于执行条件 | 仅在极端条件下发生 |
| 影响 | 导致里程碑顺延 > 2 周，或合规否决、范围被迫削减 | 顺延 1–2 周，或需局部返工 | 顺延 < 1 周，可内部消化 |

### 1.3 应对策略定义

| 策略 | 含义 | 本项目典型用法 |
|---|---|---|
| 规避 | 改变方案使风险不再存在 | 大模型不进实时告警主链路 |
| 转移 | 把后果转给第三方 | 云端 API 的可用性由 Provider SLA 承担，本地做熔断 |
| 减轻 | 降低概率或影响 | 容器内存限额、门禁复核、缓冲周 |
| 接受 | 承认风险并预留应急资源 | 3D 帧率不达标时接受降级方案 |

**分区规则**

| 区域 | 风险值 | 管理要求 |
|---|---|---|
| 红区（须主动干预） | 9 | 必须有具体缓解动作 + 明确触发点 + 阶段门禁逐条复核 |

## 4. Top 5 风险详述

### 4.1 R-06 WSL2 内存不足导致整栈 OOM（风险值 9）

| 项 | 内容 |
|---|---|
| 现象 | 多个容器同时启动后系统可用内存耗尽，内核 OOM Killer 随机杀死进程（常见于 TDengine 与 Redpanda），表现为服务反复重启、前端数据断流 |
| 根因 | ① 组件默认缓存策略按物理机内存设定，未针对 8 GB 配额收敛；② 时序库与消息队列同时持有大量页缓存；③ WSL2 的 `.wslconfig` 未限制内存上限，Docker Desktop 又各自持有配额，形成双重占用；④ 开发期常驻前端 dev server 与调试工具，隐性占用 1 GB 以上 |
| 缓解动作 | ① `.wslconfig` 设 `memory=8GB`、`swap=2GB`；② 每个 compose 服务显式 `mem_limit`（TDengine 2 GB、Redpanda 1.5 GB、PG 512 MB、Redis 256 MB、各微服务 256–512 MB、前端 256 MB）；③ TDengine 调小 `buffer`、`cacheSize`、`vgroups`，Redpanda 限制 `--memory`；④ 采集模拟器与后端共容器部署以减少开销；⑤ P4 首周做内存基线测量，形成「服务-内存」台账；⑥ 保留「关闭 3D 场景 + 关闭 RAG 服务」的低配运行模式 |
| 残余风险 | 峰值压测（600 点/秒 + 3D 渲染 + RAG 检索同时进行）仍可能触顶。残余等级：中。对策为压测时按场景分离执行，并在论文中如实标注「单机 8 GB 为原型约束，生产按 3 节点集群规划」 |

### 4.2 R-08 在职备考时间不足（风险值 9）

| 项 | 内容 |
|---|---|
| 现象 | 连续数周实际完成量不足计划 70%，文档交付一拖再拖，出现「周末补进度→下周更累」的负循环 |
| 根因 | ① 排期以理想产能（3.5 人日/周）为基准，未扣除加班、家庭事务与备考本身占用的时间；② 阶段任务粒度偏大，单周难以形成「完成感」，动力衰减；③ 缺少可视化的进度反馈，偏差发现滞后 |
| 缓解动作 | ① 按周排产，每周只承诺 3 个可交付小目标，完成后即停；② 建立「滚动四周完成量」台账，用均值而非单周判断趋势；③ 设置 2 个独立缓冲周（2027-01-20、2027-04-13），非触发条件不得动用；④ 预设三级裁剪预案，把「砍范围」变成预先授权的动作而非临时妥协；⑤ 考试前 8 周强制切换为论文优先模式 |
| 残余风险 | 若实际产能降至 2.5 人日/周，31 周排期不成立，须削减 P5 约 25% 范围（移除 RAG、3D 降级为 2.5D）。残余等级：高，属本项目的首要不确定性 |

### 4.3 R-17 范围蔓延（风险值 9）

| 项 | 内容 |
|---|---|
| 现象 | 周计划中出现未列入 WBS 的任务；讨论中频繁出现「既然都做了采集，不如把工单也接上」类提议；文档章节不断增厚但结论未增加 |
| 根因 | ① 动环运维岗位本身与系统边界模糊，日常工作中的合理诉求容易转化为开发需求；② 本人既是需求提出者又是实现者，缺少外部约束；③ 「做全一点论文更好写」的动机与范围控制天然冲突 |
| 缓解动作 | ① 范围外清单（IT 设备监控、视频分析、计费工单、移动端）写入背景卡并作为验收依据；② 所有新增需求必须走 CR，做影响分析后进入「二期清单」，不在当期实施；③ 每周复盘检查「本周是否有计划外任务」，有则记录并追溯来源；④ 论文写作以「已实现的取舍」为素材，而非以「功能数量」为卖点 |
| 残余风险 | 二期清单本身会膨胀，可能诱发「提前开工」。残余等级：低。对策为二期清单一律不排期、不估算 |

### 4.4 R-12 金融数据外发合规风险（风险值 6）

| 项 | 内容 |
|---|---|
| 现象 | 信息安全部在架构评审中提出反对：任何告警文本送入外部大模型 API 均视为数据外发，需按外发流程审批，且不得包含可定位到具体机房与设备的信息 |
| 根因 | ① 金融机构对数据出网采取默认禁止原则；② 告警文本天然含设备名、机房编号、时间戳，组合后可推断物理布局；③ 云端 API 的数据留存策略不受本方控制 |
| 缓解动作 | ① 架构上将大模型定位为**旁路增强**，不进实时告警主链路，断网不影响告警；② 送前脱敏：设备名与机房编号哈希化、位置泛化为「A 区/B 区」、数值转为区间标签、时间戳粗化到分钟；③ 仅送聚合后的告警摘要，不送原始时序与拓扑全图；④ 外发内容本地留档，可按请求追溯；⑤ 提供「纯本地模式」开关，默认可关闭外发；⑥ 由信息安全部书面确认脱敏规则后再开启 |
| 残余风险 | 脱敏规则的完备性难以自证，仍可能存在重识别风险。残余等级：中。对策为在论文中把「合规约束如何反向塑造架构」作为架构决策的论据，而非回避该问题 |

### 4.5 R-01 时序库写入瓶颈（风险值 6）

| 项 | 内容 |
|---|---|
| 现象 | 压测时写入延迟从毫秒级上升到数百毫秒，P99 入库时延超过 2 s 目标；查询与大屏刷新相互拖慢 |
| 根因 | ① 单节点单机部署，写入与查询争抢 IO 与内存；② 表设计不当（一设备一张表或标签基数过高）导致元数据膨胀；③ 逐条写入未批量；④ 幂等去重依赖额外索引，放大写入成本 |
| 缓解动作 | ① 采用「超级表 + 标签（机房/设备类型/设备 ID）」建模，按设备类型建子表，控制标签基数；② 写入端批量攒批（200–500 条或 200 ms 触发）；③ 幂等键使用「设备 ID + 测点 + 时间戳」写入唯一约束，避免二次查库；④ 查询走 Redis 缓存 + 降采样表，大屏不直接查原始表；⑤ 先以 400 点/秒基准验收，600 点/秒峰值单独记录并标注为「压测场景」 |
| 残余风险 | 真实 2000 测点长期运行的写入稳定性无法在原型环境完整验证。残余等级：中。论文中标注「设计约束，未实测」 |

## 5. 风险监控机制

| 机制 | 频次 | 内容 | 输出 |
|---|---|---|---|
| 门禁复核 | 每阶段 1 次 | 逐条核对红区/黄区风险状态：已关闭 / 仍存在 / 已发生 | 门禁检查表「风险复核」栏 |
| 周度自检 | 每周 | 检查 R-08 的实际产能偏差、R-17 的计划外任务数 | 周报中「风险信号」一行 |
| 触发式再评估 | 事件驱动 | 出现新征兆（如首次 OOM、首次合规质疑）即评估是否新增风险或调整等级 | 风险登记册增补 |
| 阶段末复盘 | 每阶段末 | 记录已发生风险的实际影响与措施有效性，更新残余风险 | 门禁记录「复盘」小节 |
| 全量再评估 | P2 末、P5 末 | 架构定稿与功能完成后各做一次全量重评，防止早期评估失效 | 风险登记册 v0.x 升版 |

**升级规则**：任一风险实际发生且影响超过 1 周，直接升级至发起人（运维主管）；涉及合规的风险不经中间层，直接同步信息安全部。

## 6. 应急预案

### 6.1 WSL2 内存不足（OOM）

| 步骤 | 动作 | 判定 |
|---|---|---|
| 1 | `docker stats` 定位内存占用 Top3 容器 | 30 s 内完成 |
| 2 | 临时降级：停 3D 前端与 RAG 服务，保留采集→告警→存储→2D 链路 | 告警链路必须保留 |
| 3 | 下调 TDengine 缓存与 Redpanda 内存参数，重启受影响容器 | 重启后观察 10 min |
| 4 | 若仍 OOM，缩减采集模拟器并发（测点数从 2000 降至 800） | 记录降级参数 |
| 5 | 事后：更新「服务-内存」台账，把该组合加入禁用清单 | 当周完成 |

### 6.2 大模型 API 不可用

| 步骤 | 动作 | 判定 |
|---|---|---|
| 1 | 熔断器触发（连续 3 次超时或 429），自动切换为纯规则模式 | 自动，无需人工 |
| 2 | 前端在 AI 面板显示「增强能力暂不可用，告警功能正常」 | 文案固定，不引起误判 |
| 3 | 检查 Provider 状态页；超过 2 h 未恢复则切换备用 Provider（若已配置） | 2 h 阈值 |
| 4 | 期间产生的待处理请求直接丢弃，不做补偿重放（避免恢复后请求风暴） | 丢弃策略固定 |
| 5 | 事后：把本次降级过程记录为论文「降级设计」的实测素材 | P7 使用 |

### 6.3 Git 冲突（双设备）

| 步骤 | 动作 | 判定 |
|---|---|---|
| 1 | 停止提交，先 `git status` 与 `git log --oneline -5` 确认两侧提交 | 不做 `reset --hard` |
| 2 | 若为文档冲突：以内容更完整的一侧为基准手工合并，另一方差异逐段并入 | 保留双方结论 |
| 3 | 若为代码冲突：以 `main` 上较新一侧为基准，另一侧改动整理为补丁后重放 | 禁止整文件覆盖 |
| 4 | 若冲突不可判定：新建 `exp/conflict-<日期>` 分支保存两侧，回到上一个 tag 重新实施 | 保证主线可运行 |
| 5 | 事后：把冲突文件加入「单设备编辑清单」，规定该文件只在固定设备上改 | 减少复发 |

### 6.4 设备损坏导致进度中断

| 步骤 | 动作 | 判定 |
|---|---|---|
| 1 | 立刻在备用设备 `git clone` 并检出最近 tag，确认文档与代码完整 | 30 min 内可恢复工作 |
| 2 | 恢复运行环境：按 P4 环境搭建手册执行，镜像从本地 tar 或镜像源拉取 | 依赖手册可复现性 |
| 3 | 重跑门禁检查表中的「环境可用性」项，确认基线一致 | 通过后继续 |
| 4 | 若两台设备同时不可用超过 1 周：启动论文优先模式，用已有文档完成素材整理，编码阶段整体顺延 | 论文不受阻 |
| 5 | 事后：确认所有制品均在远端仓库，本地不留唯一副本 | 每次阶段末核查 |

> 应急原则：任何应急动作都不得以「跳过门禁」为代价；降级可以，静默降级不允许——所有降级必须留记录并在论文中如实说明。

## 论文可引用段落

> 立项阶段我按六个类别完成风险排查，形成 21 条风险登记册，并按概率与影响的乘积划分红、黄、绿三区。风险值最高的三项分别是本地内存不足、在职投入不足与范围蔓延，说明本项目的首要威胁不在技术难点而在执行条件。对时序库写入瓶颈，我采取建模与批量化而非堆硬件：超级表加标签、控制标签基数、写入端攒批与幂等键去重，基准按 400 点每秒验收，600 点每秒峰值单独压测并如实标注为设计约束。对大模型幻觉，我没有采用不可验证的提示词优化，而是改变架构定位——大模型只出建议不出结论，根因判定由规则引擎承担，从而把不可控的输出质量隔离在告警主链路之外。（适用：「风险管理」「可靠性设计」「架构评估」类命题）
