## 1. 设计目标与约束

### 1.1 五个目标

| # | 目标 | 度量 | 达成手段 | 本文位置 |
|---|---|---|---|---|
| G-1 | **口径一致** | 同一字段在 PG 与 TDengine 中类型可映射、枚举码值一致 | 字典为唯一来源；TDengine 侧 `tinyint/smallint` 存码值，PG 侧 `varchar` 存英文值，两者用 E1/E14/E15 的码值表对齐 | §3、§4.3 |
| G-2 | **写不阻塞读** | 400 点·秒⁻¹ 写入下，180 天区间查询 P99 ≤ 3 s（目标） | 时序与事务分离；PG 只承担 5 万行/天量级的追加写；分区裁剪 + 降采样路由 | §3.4、§5 |
| G-3 | **可清理** | 超期数据清理不产生表膨胀 | 7 张表按月/年分区，`DROP TABLE`（分区）替代 `DELETE` | §6 |
| G-4 | **可重算** | 任一降采样窗口可由原始明细复现 | `agg_version` 版本列 + 覆盖写 + 区间定位 SQL | §7 |
| G-5 | **单机可跑** | 8 GB 内存 / 75 GB 磁盘内成立 | 索引总量控制在 83 个对象；PG `shared_buffers` 64 MB；不建独立表空间 | §8 |

### 1.2 硬约束（不是选择，是前提）

| 约束 | 来源 | 对设计的影响 |
|---|---|---|
| 单机单盘、8 GB 内存、8 vCPU | C-01 / C-08 | 不做读写分离、不做表空间隔离、不建物化视图（会与业务表争 `shared_buffers`） |
| **分区表的唯一约束必须包含全部分区键列** | PostgreSQL 硬限制 | `raw_alarm`、`alarm_event`、`audit_log`、`linkage_record`、`ticket_link` 五张表的业务唯一键必须退化，见 §3.5 D-3 |
| KEEP / DURATION 是**库级**参数，不可按表设置 | TDengine 3.x | 三档保留期（180 天 / 3 年 / 5 年）无法共存于一个库，必须拆库，见 §3.5 D-2 |
| 表内首个时间戳列即主键，同表内 `ts` 唯一 | TDengine 3.x | 子表必须按**测点**建：一测点一子表，`ts` 即该测点的采样时刻，同设备多测点同毫秒不冲突；若按设备建子表则多测点会互相覆盖，用微秒偏移规避又违反 FR-M1-06（偏差 0），故不采用。见 §4.2 与 §3.5 D-1 |
| 枚举值禁止中文入库 | 数据字典 §2.5 | 全部枚举列加 `CHECK ... IN (英文值)`，中文只在展示层 |
| 审计表只追加 | NFR-SEC-03 | 三重手段：权限回收 + 行级/语句级触发器 + 分区归档，见 §3.3 代码块 7 与 §6.3 |

## 2. 设计原则

### 2.1 命名（沿用字典 §2，本文只补物理对象）

| 对象 | 规则 | 示例 |
|---|---|---|
| Schema | 单一 `cdcim`，不用多 schema 分域 | `cdcim.alarm_event` |
| 表 | 全小写单数 `snake_case`，≤ 32 字符 | `telemetry_late_bypass` |
| 主键约束 | `pk_<表名>` | `pk_alarm_event` |
| 唯一约束 | `uk_<表名>_<语义>` | `uk_point_def_code` |
| 普通索引 | `idx_<表名>_<列简写>` | `idx_raw_alarm_dev_ts` |
| 部分索引 | 同上，谓词写在 `WHERE` | `idx_device_online ... WHERE online_status <> 'online'` |
| 特殊访问方法 | `brin_` / `gin_` 前缀 | `brin_audit_log_created` |
| CHECK | `ck_<表名>_<语义>` | `ck_alarm_rule_level` |
| 外键 | `fk_<表名>_<引用表>` | `fk_point_def_device` |
| 月分区 | `p_<表名>_<yyyymm>` | `p_raw_alarm_202611` |
| 年分区 | `p_<表名>_<yyyy>` | `p_energy_metric_daily_2027` |

### 2.2 主键策略

| 策略 | 适用 | 理由 |
|---|---|---|
| `bigint GENERATED ALWAYS AS IDENTITY` 代理主键 | 17 张单列主键表 | 与字典 §2.3 一致；`ALWAYS` 禁止应用层显式插入 ID，避免导入脚本把序列写歪 |
| 联合主键 | `user_role(user_id, role_id)`、`role_permission(role_id, perm_id)` | 纯关系载体，加代理主键只会多一个无用索引 |
| 业务唯一键独立于主键 | 每张主数据表 1 个 `*_code` | 人工检索与外部系统对接走 `uk_`，不依赖自增值 |
| **不使用 UUID** | 全部 | 随机 UUID 会让 B-Tree 插入点分散，300 行的表无收益；`request_id` 用 UUID 但只做唯一键不做主键 |

### 2.3 时间字段

| 规则 | 落地 |
|---|---|
| 绝对时刻一律 `timestamptz(3)` | 18 张表共 64 个时刻列，无一例外 |
| 日粒度用 `date` | `install_date`、`stat_date`、`effective_from`（知识库） |
| 服务端时钟，不用客户端时间 | `created_at DEFAULT now()`；审计表额外由应用层覆写，禁止信任入参 |
| 库级时区固定 UTC | 建库时 `ALTER DATABASE cdcim SET timezone = 'UTC'`，展示层转换 |
| 单调不回退 | 时序表由 TDengine 主键保证；PG 侧不做强制（`updated_at` 允许回拨，仅作审计参考） |

### 2.4 软删除

**本系统不做通用软删除**，按数据性质分三类处理：

| 类别 | 表 | 删除语义 |
|---|---|---|
| 台账类 | `device`、`space_node`、`point_def`、`user_account`、`role` | **禁止物理删除**：用状态列退役（`lifecycle_status='retired'` / `point_status='disabled'` / `account_status='disabled'`），外键 `RESTRICT` 在库层兜底 |
| 事件/日志类 | `raw_alarm`、`alarm_event`、`audit_log`、`linkage_record` | 不删除，超期由分区整块淘汰（§6） |
| 配置类 | `alarm_rule` | `rule_status='archived'` 归档，历史版本按 `(rule_code, rule_version)` 并存 |

**为什么不用 `deleted_at` 统一软删除**：软删除会让每个查询都带 `WHERE deleted_at IS NULL`，一旦漏写就是数据泄漏；而本系统的删除需求全部能被「状态列 + 外键 RESTRICT」表达，多一个通用列只会增加漏写风险。

### 2.5 审计

| 规则 | 落地 |
|---|---|
| 写操作统一走审计切面 | 不依赖各服务自觉，统一在 API 层拦截后写 `audit_log` |
| 操作人存双份 | `actor_id` + `actor_name` 快照，不建外键（字典 §3.2 刻意不建联系之一） |
| 防篡改 | `prev_hash` + `record_hash` 组成哈希链；库层禁止 `UPDATE`/`DELETE`/`TRUNCATE` |
| 变更留痕 | `before_value` / `after_value` 只记被改字段，且**参数摘要脱敏** |
| 高风险操作单独标记 | `risk_level='high'` 对应控制类、越权、导出；由权限点的 `is_sensitive` 驱动 |

### 4.2 子表与写入

```sql
-- 子表按测点建：一测点一张，命名 m_<point_id>，共 2 000 张；设备台账新增测点时懒建
CREATE TABLE IF NOT EXISTS dcim.m_7001 USING dcim.st_metric
    TAGS (1001, 1, 30012, 'ups', 1);   -- device_id / room_id / rack_id / device_type / critical_flag

-- 批量写入：同一测点的多行合并为一条 INSERT，自动建表 + 写 TAGS
INSERT INTO dcim.m_7001 USING dcim.st_metric
    TAGS (1001, 1, 30012, 'ups', 1)
VALUES
    ('2026-11-27 10:00:03.000', 7001, 221.35, NULL, NULL, 0, 0, 22135, '2026-11-27 10:00:03.180', 'b20261127-1000', 0),
    ('2026-11-27 10:00:08.000', 7001, 221.40, NULL, NULL, 0, 0, 22140, '2026-11-27 10:00:08.176', 'b20261127-1000', 0);
```

**写入约定（D-1 修订的落地，必须由 stream-compute 实现）**：

| 规则 | 说明 |
|---|---|
| `ts` 即原始采样时刻 | 写入 `ts = ts_sample`，**不做任何偏移**。子表内只有这一个测点，不存在「同设备多测点同毫秒争主键」的问题，冲突在建模层已消失——这是选择一测点一子表的根本原因（FR-M1-06 要求补传时间戳与原始采集时刻偏差 0，任何偏移都是数据失真） |
| `point_id` 列 | 冗余保存并在写入时校验与子表 TAG 一致；仅用于跨子表联邦查询与数据校验，**不再作为过滤条件**（过滤由子表定位承担） |
| 回放与补传 | `ts_source = 2(replay)` 走「同 `ts` 覆盖」，与在线写入同一口径，可重现同一行 |
| 子表不删除 | 测点停用只置 `point_status='disabled'` 并停写，不删表（删表即丢历史）；`CREATE TABLE IF NOT EXISTS` 幂等，重复调用无副作用 |

**子表规模**：原始 **2 000 张**（一测点一表）+ 降采样 **3 × 2 000 = 6 000 张**，合计 **8 000 张**。元数据约 8 000 × 4 KB ≈ **32 MB**，相对 40 GB 数据量可忽略；TDengine 本身面向百万级子表设计，8 000 张不构成元数据或建表开销压力。建删时机：台账新增测点时建 1 张原始子表 + 3 张降采样子表（共 4 张，即 8 000 ÷ 2 000）；测点停用只打 `point_status` 标记、不删表。

### 4.3 为什么不用 TDengine 内置 STREAM 做降采样

| 候选 | 结论 | 理由 |
|---|---|---|
| `CREATE STREAM` 窗口聚合 | **不采用** | 聚合逻辑会变成 SQL / 流任务里的第二份实现，与「重算任务读历史 + 同一 `aggregate()` 函数」形成两套口径——《数据架构》§3.3 选简化流式的核心论据就是「单套代码」。用 STREAM 等于在时序库侧重新长出 Lambda 的批流双实现问题 |
| Python 外部聚合（**采用**） | 水位线推进后批量写 `USING ... TAGS` | 与在线计算、重算共用同一函数库；代价是 60 s 窗口延迟由应用保证，不享受库内计算下推 |
| 连续查询 / 定时 SQL | 不采用 | 3.x 无 CQ（TDengine 2.x 的 `CREATE STREAM` 语义已变），且同样引入两套实现 |

### 4.4 索引能力边界

TDengine 3.x **没有 B-Tree 二级索引**，可用加速手段只有四种，本文逐一对应：

| 手段 | 本文用法 | 解决什么 |
|---|---|---|
| TAG 过滤 | `WHERE device_id = 1001` / `room_id = 1` / `device_type = 'ups'` | 把扫描范围收敛到一个 vgroup 的若干子表；TAG 有内置倒排 |
| 时间分区裁剪 | `WHERE ts >= ? AND ts < ?` | 只打开覆盖区间的数据文件组（`DURATION 10d` → 180 天约 19 组） |
| `last_row` / `last_value` 缓存 | `CACHEMODEL 'both'` | 「取最新值」不扫表，支撑大屏 5 s 刷新 |
| 列过滤 | `WHERE point_id = ?` | 子表已按测点定位，列过滤只作校验与跨子表联邦查询的补充手段，**不再承担过滤职责**，放大系数为 1 |

**结论**：TDengine 侧的「索引设计」实质是「TAG 设计与子表粒度设计」，已在 4.2 与字典 §4.5 定死；本文不再新增任何物理索引对象。

## 5. 索引与查询优化

### 5.1 示例 1：180 天单测点曲线（TDengine）

```sql
-- 180 天 → 按 bucket ≥ interval / max_points 路由到 1 h 表（《容量规划》§3.3 公式）
-- 子表即测点，表名由 point_id 直接派生，无需再按 point_id 过滤
SELECT ts, val_avg, val_max, val_min, valid_count, quality_flag
FROM   dcim_1h.m_7001
WHERE  ts >= '2026-06-01 00:00:00.000'
  AND  ts <  '2026-11-28 00:00:00.000'
ORDER BY ts;
```

| 执行步骤 | 动作 | 代价 |
|---|---|---|
| ① 表定位 | 客户端按 `point_id` 直接拼出子表名 `m_7001`（一测点一子表，无需经 `device_id` 映射） | 0（字符串拼接） |
| ② 分区裁剪 | `DURATION 365d` 的 `dcim_1h`，180 天落在 1 组数据文件内 | 打开文件数 1 |
| ③ 列扫描 | 读取 `ts` / `point_id` / 5 个度量列，跳过其他列（列存天然只读所需列） | 读 4 320 行 |
| ④ 过滤 | 无行级过滤（该子表只含 1 个测点），仅时间区间裁剪 | 0 |
| ⑤ 排序 | `ts` 天然有序，无 sort | 0 |

**命中说明**：无索引可命中，全靠分区裁剪与子表定位，而子表定位的精度由「一测点一子表」保证——不存在「同一张表里混了同设备 7 个测点、只能靠列过滤」的放大。若误路由到原始表（`dcim.st_metric`，5 s 粒度），8 条曲线叠加扫描约 2 490 万行、约 1.24 s，虽仍在 3 s 内，但已占去 41% 预算，与 8 条曲线的渲染耗时叠加后余量不足——**路由判错仍是最危险的单点错误，只是后果从「必然超时」变为「余量被吃掉」**。

### 5.2 示例 2：告警工作台列表（PG）

```sql
SELECT event_id, event_code, event_title, alarm_level, event_status,
       last_occur_at, root_device_id
FROM   cdcim.alarm_event
WHERE  event_status IN ('raised','acknowledged')
  AND  alarm_level  = 'critical'
  AND  first_occur_at >= now() - interval '30 days'  -- 裁剪谓词（粗）：命中的月分区必在此范围
  AND  last_occur_at  >= now() - interval '7 days'   -- 过滤谓词（精）：业务口径「近 7 天」
ORDER BY last_occur_at DESC
LIMIT  50;
```

| 执行步骤 | 动作 | 依据 |
|---|---|---|
| ① 谓词分工 | 粗谓词打分区键 `first_occur_at`、精谓词打 `last_occur_at` | **分区键是事件首次发生时刻，而业务要按最近发生排序**，两者不是一列。只用 `last_occur_at` 过滤时 Planner 必须扫全部 14 个分区（待确认 2） |
| ② 分区裁剪 | 粗谓词 30 天 → 只保留 2 个月分区（其余 12 个被排除） | 分区键与谓词同列，裁剪生效 |
| ③ 索引扫描 | `idx_alarm_event_status(event_status, alarm_level, last_occur_at DESC)`：两列等值 + 第三列范围，索引序即 `ORDER BY` 序 | 三列完全覆盖谓词与排序 |
| ④ 早停 | `LIMIT 50` 命中 50 行即返回，不扫完索引 | 工作台首屏只取 50 条 |
| ⑤ 回表 | 取 `event_title` 等未在索引中的列 | 50 次随机读 |

**一处必须诚实说明的取舍**：粗谓词取 **30 天**（待确认 2，已按裁决由 8 天放宽）。它不再是「8 天」那样紧的口径，代价是分区裁剪命中 2 个月分区而非 1 个（多扫 1 个分区的索引段），换来的是「检修挂起」场景下事件跨度超过 8 天也不被误裁——`suppress_expire_at` 可让事件挂起数天，因此 8 天的业务假设不成立。双谓词分工不变：`first_occur_at` 只负责分区裁剪，`last_occur_at` 负责精确过滤与排序。**这是查询约束而非索引缺陷**——索引本身已经完全覆盖谓词与排序。

### 5.3 示例 3：审计按人检索（PG）

```sql
SELECT audit_id, audit_no, operation_type, operation_result,
       actor_name, target_type, target_id, created_at
FROM   cdcim.audit_log
WHERE  actor_id = 1024
  AND  created_at >= '2026-09-01 00:00:00+00'
  AND  created_at <  '2026-10-01 00:00:00+00'
ORDER BY created_at DESC
LIMIT  100;
```

| 执行步骤 | 动作 | 依据 |
|---|---|---|
| ① 分区裁剪 | 区间 = 1 个月 → 只扫 `p_audit_log_202609`（约 150 万行），其余 16 个分区排除 | 分区键 `created_at` 与谓词同列，裁剪直接生效 |
| ② 索引扫描 | `idx_audit_log_actor(actor_id, created_at DESC)`：等值 + 范围，且索引序即排序序 | 单人单月约 800 行 |
| ③ 早停 + 回表 | `LIMIT 100`，100 次回表 | — |
| ④ BRIN 为何不参与 | `brin_audit_log_created` 适合「无过滤条件的全时间范围扫描」（如整月导出、归档校验），索引只存块级 min/max；本查询已有更精确的复合 BTree，Planner 会选后者 | 两者分工，不是冗余 |

**一条反例说明 BRIN 的价值**：归档校验要「按 `created_at` 扫整月并逐条验 `record_hash` 链」，无 `actor_id` 过滤，此时 BTree 无用（会走全表顺序扫），BRIN 虽也被顺序扫绕过，但其 0.4 MB 的体积优势体现在**分区裁剪失败时的兜底**（如跨 3 个月无谓词查询）。BRIN 在本项目的真实收益是**体积**而非**加速**：1 825 万行的 BTree 约 400 MB，会挤占 64 MB `shared_buffers` 之外的页缓存。

### 6.2 分区维护（每月一次，apscheduler 定时）

```sql
-- 1) 建下月分区：若存在 DEFAULT 分区，须先摘除再建（DEFAULT 会阻止新分区创建）
ALTER TABLE cdcim.raw_alarm DETACH PARTITION cdcim.p_raw_alarm_default;
CREATE TABLE cdcim.p_raw_alarm_202612 PARTITION OF cdcim.raw_alarm
    FOR VALUES FROM ('2026-12-01 00:00:00+00') TO ('2027-01-01 00:00:00+00');
ALTER TABLE cdcim.raw_alarm ATTACH PARTITION cdcim.p_raw_alarm_default DEFAULT;
```

> **DEFAULT 分区的代价**：只要存在 DEFAULT 分区，新建区间分区前必须 `DETACH` 它（否则 PG 需扫描 DEFAULT 校验无越界行，大表下会长时间持锁）。本文仍保留 DEFAULT，理由是「宁可慢一次也不丢数据」——采集侧写入若落在未预建月份，DEFAULT 兜住；代价是月度维护脚本多两步。

### 6.3 归档流程（每日 03:00）

```sql
-- 步骤 1：选出到期分区（示例：审计表 2025-08 月分区）
SELECT c.relname AS part_name,
       pg_get_expr(c.relpartbound, c.oid) AS bound
FROM   pg_class c
JOIN   pg_inherits i ON i.inhrelid = c.oid
JOIN   pg_class p    ON p.oid = i.inhparent
WHERE  p.relname = 'audit_log'
  AND  c.relname LIKE 'p_audit_log_%'
  AND  c.relname < 'p_audit_log_' || to_char(now() - interval '16 months', 'YYYYMM')
ORDER BY c.relname;

-- 步骤 2：摘除（秒级，元数据操作；此时数据仍可查，作为回滚窗口）
ALTER TABLE cdcim.audit_log DETACH PARTITION cdcim.p_audit_log_202508;

-- 步骤 3：导出 + 校验 record_hash 链（应用侧执行，非 SQL）
--   校验通过 → 写一条审计（operation_type='delete', target_type='system'）→ 步骤 4
--   校验失败 → 中止，重新 ATTACH 回去，发 critical 告警

-- 步骤 4：物理删除（瞬时释放空间，无 VACUUM 依赖）
DROP TABLE cdcim.p_audit_log_202508;
```

**三条硬规则**（与《数据架构》§7.3 一致）：

1. **先校验后删除**：审计表必须验 `record_hash` 链完整，失败则 `ATTACH` 回滚并告警；
2. **只用分区操作**：禁 `DELETE`（死元组 + 索引膨胀 + 依赖 `VACUUM`）；`DETACH` 与 `DROP` 分两步，中间留可回滚窗口；
3. **销毁也留痕**：`DROP` 本身写一条 `audit_log`（`operation_type='delete'`，`target_type='system'`），否则「数据已删除」无法自证合规。

### 6.4 清理任务与监控

| 任务 | 频率 | 判据 | 失败动作 |
|---|---|---|---|
| 预建下月分区 | 每月 1 日 02:00 | 目标分区不存在 | 告警 `partition_missing`（写入会落 DEFAULT，业务不中断） |
| 归档扫描 | 每日 03:00 | `relname < now() - 保留期` | 中止 + 告警，不删任何东西 |
| 审计链校验 | 归档前 + 每日抽样 1 个分区 | 哈希链连续 | 中止 + 告警 |
| 分区数量巡检 | 每日 | 单表分区数 ≤ 预建数 + 2 | 告警 `partition_sprawl`（说明预建逻辑失效） |
| `VACUUM` 巡检 | 每周 | 非审计表死元组占比 > 10% | 对事件表执行 `VACUUM (ANALYZE)`；审计表不做（无更新） |

## 7. 重算接口的数据支撑

### 7.1 问题定义（来自场景视图 S-2）

断网 30 min 的数据补传后，**明细完整率 100%，聚合修正率 0%**——因为补传数据的时间戳早于 60 s 水位线，全部进 `telemetry_late_bypass`，已发布的降采样不会被修正。P3 必须提供「按时间区间重算降采样」的**数据能力**（接口契约见 P3 接口文档，本文只答「库表能支撑什么」）。

### 7.2 可重算范围（由 KEEP 决定，不可越界）

**表 TAB-DB-005　三类数据的可查/可重算边界**

| 数据 | 库 / 表 | KEEP | 可重算范围 | 超出后的替代 |
|---|---|---|---|---|
| 秒级明细 | `dcim.st_metric` | 190 天（设计 180 + `DURATION` 余量） | 最近 180 天可**从明细重建任意粒度** | 只能重算到 1 min 粒度（无法恢复秒级） |
| 1 min 聚合 | `dcim_1m.st_metric_1m` | 1 095 天 | 最近 3 年可**从 1 min 重建 5 min / 1 h** | 超出 3 年：1 h 仍在，可查到 5 年 |
| 5 min / 1 h | `dcim_5m` / `dcim_1h` | 1 095 / 1 825 天 | 只可覆盖写，不可向上重建 | 超出即不可查 |

**三条边界必须写进接口契约**：① `start` 早于 180 天时，重算目标只能到 1 min 粒度，接口须返回 `degraded=true` 并说明；② `start` 早于 1 095 天时拒绝（`409`），不允许「部分重算」造成口径断裂；③ 跨 180 天边界的区间，按「明细段 + 1 min 段」两段拼接重算，拼接点须对齐到整分。

### 7.3 重算的定位与版本

```sql
-- ① 定位受影响窗口（以 1 min 为例）：重算前先算出「哪些窗口有风险」
--    数据源：迟到旁路表（PG）——它是唯一记录了「本该落入哪个窗口」的地方
SELECT original_window AS win_start,
       date_trunc('hour', original_window) AS hour_start,
       count(*)        AS late_rows
FROM   cdcim.telemetry_late_bypass
WHERE  device_id = 1001
  AND  point_id  = 7001
  AND  process_status = 'pending'
  AND  ts >= :start AND ts < :end
GROUP BY 1, 2
ORDER BY 1;

-- ② 读原始明细算新值（TDengine，与在线聚合同一个 aggregate() 函数）
--    :win_end 由应用侧算好（win_start + 1 min），TDengine 不支持在谓词里做 interval 运算
--    子表即测点：m_7001，无需 point_id 过滤
SELECT ts, point_id, val_double, quality
FROM   dcim.m_7001
WHERE  ts >= :win_start AND ts < :win_end
ORDER BY ts;

-- ③ 覆盖写：同一 ts 重写（子表内唯一键即 ts），agg_version + 1（TDengine 后到覆盖）
--    INSERT INTO dcim_1m.m_7001 USING dcim_1m.st_metric_1m TAGS (...) VALUES (...);
```

**版本过滤方案（不新增字段，只用 `agg_version`）**：

| 环节 | 做法 | 依据 |
|---|---|---|
| 重算标识 | 同一窗口重算后 `agg_version = 旧值 + 1` | 字典 §4.6「迟到数据触发重算时 +1」 |
| 下游判断 | 报表/缓存侧记住「上次读到的 `agg_version`」，发现变大即失效缓存 | 只读一列，无需建表 |
| 缓存失效 | `cdcim:cache:overview:*` TTL 60 s 自然失效，不主动删（避免「删缓存」引入新的一致性路径） | 《数据架构》§5.3 |
| 重算留痕 | 每次重算写 1 条 `audit_log`（`operation_type='update'`、`target_type='system'`、`action_detail` 含区间/粒度/窗口数/版本） | 复用现有表，**不新增重算任务表** |
| 幂等 | 重算 = 覆盖写，重跑无副作用；区间按天切片，中断只损失当前天 | 《数据架构》§3.4 代价表 |

> **为什么不为重算建任务表**：重算任务的进度可由「已处理的天数 + Prometheus 计数器」表达，落表会引入「任务状态与数据状态不一致」的新问题（任务说完成、数据没写完）。当前设计下重算的唯一权威状态是「`agg_version` 是否变大」，这是可验证的，任务表不是。

### 7.4 重算的三条约束

| # | 约束 | 违反后果 |
|---|---|---|
| 1 | 重算必须复用在线聚合的同一个 `aggregate()` 函数 | 否则重新长出批流双实现，误差不可控（FR-M2-03 要求 ≤ 0.5%） |
| 2 | 重算级联：1 min 变 → 5 min 变 → 1 h 变，三级都要重写 | 只改 1 min 会造成「1 min 与 1 h 对不上」，比不重算更糟 |
| 3 | 重算限速：单批 ≤ 5 000 行、并发 1、默认 02:00 执行 | 与在线查询争单盘 IO（《容量规划》§5 瓶颈 2） |

### 8.2 三处与 DB 设计直接相关的容量判断

| # | 判断 | 数据 | 对 DB 设计的影响 |
|---|---|---|---|
| 1 | **索引占用可忽略，但审计表 BRIN 是必需** | 83 个索引合计约 0.6 GB；若审计 `created_at` 用 BTree 则单独 400 MB | 审计表 BRIN 不是「优化」而是「省下 400 MB 页缓存」——在 64 MB `shared_buffers` 下，400 MB 索引会让热数据被挤出 |
| 2 | **子表 8 000 张，元数据 32 MB** | 原始 2 000（一测点一表）+ 降采样 3 × 2 000 = 6 000 | 元数据约 8 000 × 4 KB ≈ 32 MB，占磁盘 0.04%，可接受；TDengine 面向百万级子表设计，建表与查询元数据开销均摊薄。代价转嫁到「建删时机」：台账新增测点建 1 张原始表 + 3 张降采样表，测点停用只打标签不删表 |
| 3 | **分区数上限** | 6 张月分区表 × 17 + 1 张年分区 × 6 = 108 个分区 | 每分区约 2 个索引段，总 relation 数约 500；远低于 PG 的 `max_locks_per_transaction` 风险线，但**跨全部分区的查询会持有 108 个锁**，故 §5.2 强制加裁剪谓词 |

### 8.3 扩容触发的 DB 侧动作

| 触发（《容量规划》§6.3） | DB 侧动作 | 代价 |
|---|---|---|
| 磁盘 ≥ 80% | 归档任务提前执行；`dcim` 的 `KEEP` 190 → 150 | 原始可查窗口缩短 40 天，重算深度同步缩短 |
| 测点数 → 4 000 | `st_metric` 子表 2 000 → 4 000（降采样同步 3 × 4 000，合计 16 000 张，元数据 64 MB）；`VGROUPS` 2 → 4；1 min 容量 12 → 24 GB | 需重建库参数（`VGROUPS` 不可在线改，须新建库导数据）；子表新建随台账批量导入脚本完成 |
| 审计量 ×2 | 月分区行数 150 万 → 300 万 | 分区数不变，`BRIN` 的 `pages_per_range` 32 → 64（保持每区间行数稳定） |

## 论文可引用段落

> **【适用题目类型】论数据库设计 / 论时序数据处理 / 论系统性能优化**

物理设计阶段我遇到的第一道硬墙不是性能，而是约束本身。告警表按月分区，清理靠整块删除分区而不是逐行删除，这在千万行量级上是唯一可行的方式；但分区表要求唯一索引必须包含分区键，于是原本的告警指纹唯一约束只能退化为「指纹加判定时刻」。这个退化不是妥协，因为去重窗口只有五分钟，跨月的同指纹重复在业务上不可能发生，我把这个判断写进了决策台账，而不是悄悄改掉约束。第二道墙在时序库：主键只是时间戳一列，一开始我按设备建子表，把七个测点塞进同一张表，结果同一毫秒上报的数据会互相覆盖。最省事的补法是给时间戳的微秒位加测点序号，但那样采集时刻就被改动了，而验收判据要求补传数据与原始采集时刻的偏差必须为零——一个为了绕开约束的偏移，换来的是一整套时间语义的失真。于是我推翻重做，改成一测点一子表：主键冲突在建模层消失，时间戳保持原样，代价是子表从三百张涨到八千张、元数据三十二兆，这个代价在百万级子表设计面前可以忽略。索引上一共八十三个对象，每一个都在文档里写了理由：部分索引只为异常行付代价，审计表用块级索引把四百兆压到零点四兆，因为六十四兆的共享缓冲区经不起这么大的索引。
