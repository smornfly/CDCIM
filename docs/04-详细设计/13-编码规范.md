> **口径声明**
> 1. 本文的每条规则都必须能回答「**谁在什么时机、用什么工具、以什么阈值判定**」。回答不了的条目一律不写——「保持代码整洁」「命名要有意义」这类表述对实现者零信息量，只会稀释真正可执行的条款。
> 2. 工具版本与命令为**设计约定**，P4 落盘时钉版并写入 `pyproject.toml` / `package.json` / CI 配置；本文不承诺具体版本号，避免「文档写 v0.4、实际装 v0.6」的漂移。
> 3. 规则分三级：**A 阻断**（CI 失败，不可合并）、**B 告警**（不阻断但 Must Fix 在下次提交前）、**C 评审**（机器判不了，进 PR 检查单）。分级写进每条规则的最后一列。

## 1. 适用范围与基本原则

### 1.1 适用对象

| 范围 | 内容 | 主要规则 |
|---|---|---|
| 后端 | `core/` 下 8 个包（Python 3.11） | §2、§3 |
| 前端 | `web/`（Vue3 + TypeScript + Vite） | §4 |
| 配置与规则 | `deploy/`、`alarm_rule` 的 YAML DSL、compose 文件 | §5 |
| 全仓 | 提交、分支、PR、文档与注释 | §6 ~ §8 |

本文**不规定**：代码行数上限的绝对值（只规定触发拆分的阈值）、覆盖率目标（P6 定）、性能预算（见各设计文档）。

### 1.2 三条基本原则（每条都能落到具体规则）

| 原则 | 含义 | 落地规则 |
|---|---|---|
| 可读性优先于技巧 | 代码被读的次数是写次数的十倍；看不懂的优化等于负优化 | PY-02、PY-04、FE-03 |
| 显式优于隐式 | 依赖、单位、超时、失败路径都写在调用点，不靠约定与默认值 | PY-06、PY-09、SQL-08 |
| 失败要可观测 | 每一次失败必须留下「谁、在哪、为什么、带哪个 trace」四个信息 | PY-07、PY-08、FE-06 |

一条判据帮助取舍：**如果这段代码出错时，值班员只能看到「操作失败」，那它就是不合格的**——他必须能看到错误码与 `trace_id`，运维必须能凭它定位到一次具体调用。

## 2. Python 规范

### 2.1 版本与依赖

- 解释器 **3.11**（与镜像基座一致，ADR-0002）；不使用 3.12+ 语法，避免镜像与本地不一致。
- 依赖**全量钉版本**（含传递依赖），写入 `requirements.txt`；`pyproject.toml` 只声明直接依赖与工具配置。
- 新增直接依赖需在 PR 说明「为什么标准库不够」，因为每一个依赖都会进入 8 个镜像中的至少一个（TAB-ARCH-98 的大小预算）。

### 2.4 异步与阻塞边界（唯一一处需要展开的规则）

线上故障里最难查的一类，是「一个同步调用卡住了整个事件循环」：所有接口同时变慢，监控上看不出哪个依赖出了问题。因此 PY-06 定为 A 级，并给出三条具体边界：

| 场景 | 做法 | 反例 |
|---|---|---|
| 数据库驱动为同步（psycopg） | 统一走 `await asyncio.to_thread(...)`，或在专用线程池执行 | 直接在协程里 `cur.execute(...)` |
| 文件读写（场景 JSON、导出文件） | 小文件（< 1 MB）可同步；大文件走 `to_thread` | 在协程里 `open().read()` 一个 200 MB 导出文件 |
| 外部平台调用（门禁、视频） | 必须设 `timeout`，并与接口文档的 5 s 取流超时一致 | 无限等待第三方响应 |

**超时是强制的**：任何跨进程调用都必须显式给 `timeout=`，并在超时后抛带错误码的异常（`CDCIM-EXT-001/002`）。没有超时的调用在评审中一律打回——它的失败模式是「永远不返回」，比报错更难处理。

## 3. SQL 与 DDL 规范

**表 TAB-DD-55　SQL 规则（8 条）**

| 编号 | 规则 | 正例 | 反例 | 级别 |
|---|---|---|---|---|
| SQL-01 | 表名单数 `snake_case` ≤ 32 字符；字段禁裸用 `type`/`status`/`level` | `alarm_event.alarm_level` | `alarm_event.level` | A |
| SQL-02 | 每表必须有代理主键 `<表名单数>_id`（`bigint GENERATED ALWAYS AS IDENTITY`）与 1 个业务唯一键 `*_code` | `pk_device (device_id)` | 用 `device_code` 当主键 | A |
| SQL-03 | 索引名 `idx_<表>_<列简写>`、唯一 `uk_`、主键 `pk_`、约束 `ck_`、外键 `fk_` | `idx_device_space (space_node_id)` | `device_index1` | A |
| SQL-04 | 组合索引列序 = 高频查询的等值列在前、范围列在后；每个索引必须有注释说明它服务哪个查询 | `idx_alarm_event_status (event_status, last_occur_at DESC)` 注释「告警工作台默认排序」 | 对每列各建一个单列索引 | B |
| SQL-05 | 枚举列存英文码值并加 `CHECK`；中文只出现在前端映射表 | `CHECK (alarm_level IN ('critical','major','minor'))` | 存 `'紧急'` | A |
| SQL-06 | 时间列一律 `timestamptz(3)`；禁止 `timestamp`（无时区）与 `varchar` 存时间 | `created_at timestamptz(3) NOT NULL DEFAULT now()` | `created_at varchar(19)` | A |
| SQL-07 | 迁移脚本单向、单事务、可重入：`V<yyyymmddHHMM>__<verb>_<object>.sql`，用 `IF NOT EXISTS` / `IF EXISTS` | `V202611271030__add_rack_capacity.sql` | `alter.sql`、`fix2.sql` | A |
| SQL-08 | 禁止在迁移中 `DROP COLUMN` / `DROP TABLE`；废弃分两步：先标记 `deprecated_at`，跨两个版本后再删 | 加列 `deprecated_at timestamptz` | 直接 `DROP COLUMN host` | A |

**迁移幂等的验收方式**：在空的 PG 容器上连续执行两次全量迁移，第二次必须**零报错、零 diff**（`CK-06`）。这条检查能挡住 90% 的手写 `ALTER` 事故——一次性写对的迁移很少，能重复执行的迁移才敢在生产回滚重放。

**一条关于「不建物理外键」的说明**：数据字典 §2.3 规定日志/事件类表不建外键、台账类外键 `ON DELETE RESTRICT`。规范里不重复该决策，只要求：若表属于「日志/事件」类，迁移脚本必须在文件头注释里写明「本表不建外键」及理由，否则评审无从判断是遗漏还是有意。

## 4. Vue3 / TypeScript 规范

**表 TAB-DD-56　前端规则（8 条）**

| 编号 | 规则 | 正例 | 反例 | 级别 |
|---|---|---|---|---|
| FE-01 | 组件一律 `<script setup lang="ts">`；不新增 Options API 组件 | `<script setup lang="ts">` | `export default { data() {...} }` | A |
| FE-02 | `props` / `emits` 必须显式类型；禁止 `any`，未知结构用 `unknown` + 类型收窄 | `defineProps<{ rackId: number }>()` | `defineProps(['rackId'])` | A |
| FE-03 | 目录按视图域（`views/` `charts/` `three/` `api/`），不按文件类型；单组件 > 300 行须拆分 | `three/scene/generator.ts` | `components/AllInOne.vue` 900 行 | B |
| FE-04 | Pinia 只放**跨视图共享**的状态；单视图状态用 `ref`；3D 相机、`Scene`、`Mesh` 等不可序列化对象**不得入 store** | `useAlarmStore()` 存筛选条件 | 把 `THREE.Camera` 存进 Pinia | A |
| FE-05 | 请求只经 `src/api/` 的生成客户端；禁止组件内 `fetch` / `axios` 直连，禁止硬编码地址 | `await api.getDevices({ roomId })` | `fetch('http://10.0.0.5:8000/devices')` | A |
| FE-06 | 错误按错误码前缀统一处理：`AUTH-*` 跳登录、`REQ-*` 就地提示、`SYS-*` 展示 `trace_id` | `if (code.startsWith('AUTH-')) logout()` | `alert('请求失败')` | A |
| FE-07 | 定时器、SSE、`ResizeObserver`、`requestAnimationFrame` 必须在 `onUnmounted` / `onScopeDispose` 释放 | `onUnmounted(() => es.close())` | 组件卸载后 SSE 仍在收消息 | A |
| FE-08 | 3D 资源显式释放：`geometry` / `material` / `texture` 用后 `dispose()`；渲染循环内禁止 `new` 对象 | 预分配 `Vector3` 复用 | 每帧 `new THREE.Color()` | B |

**FE-04 与 FE-07 是同类问题的两面**：3D 场景里的对象既不该进全局状态（不可序列化、无法调试回放），也不该脱离组件生命周期（离开路由后 rAF 还在跑，内存 30 min 涨 200 MB，正对应 PERF-3D-03 的「30 min 增长 ≤ 50 MB」判据）。这两条不是风格问题，是性能验收的前置条件。

**一处前端特有的边界**：`web/src/api/` 由 OpenAPI 生成（开发视图 §3），生成代码不受 FE-01 ~ FE-03 约束（不手改生成物），但 FE-05 的「只经生成客户端」正是为了保证「生成物不需要手改」。若发现必须手改，说明契约有问题，改契约而不是改生成物。

## 6. Git 与提交规范

### 6.1 分支

| 分支 | 用途 | 命名 | 生命周期 |
|---|---|---|---|
| `main` | 可构建、可演示 | — | 长期，**受保护**，禁直接 push |
| 特性 | 单个需求或设计项 | `feat/<issue>-<slug>`，如 `feat/12-scene-generator` | 合并后删除 |
| 修复 | 缺陷 | `fix/<issue>-<slug>` | 同上 |
| 文档 | 仅 `docs/` 变更 | `docs/<slug>` | 同上 |

### 6.2 提交信息

格式 `type(scope): subject`，`type ∈ {feat, fix, docs, refactor, test, chore, perf}`，`scope` 取包名（`alarm`、`web`、`deploy`）或文档编号。

```
feat(three): 按 generate 参数展开机柜阵列
fix(alarm): 抑制窗口跨天时计数溢出
docs(dd-08): 修正 Z 轴方向口径
```

要求：subject ≤ 50 字符、不加句号；正文说明「为什么改」与「影响面」；一个提交只做一件事。**反例**：`update`、`修改`、`fix bug`、`提交一下` —— 这类信息在 `git log` 里等同于空行。

### 6.3 三条可判定规则

**表 TAB-DD-58　Git 规则（3 条）**

| 编号 | 规则 | 正例 | 反例 | 级别 |
|---|---|---|---|---|
| GIT-01 | 分支名 `type/<issue>-<slug>`，`main` 受保护禁直接 push | `feat/12-scene-generator` | `dev`、`test2` | A（服务端保护规则） |
| GIT-02 | 提交信息 `<type>(<scope>): <subject>`，subject ≤ 50 字符且不含句号 | `fix(alarm): 抑制窗口跨天时计数溢出` | `修改`、`fix bug` | B（commitlint） |
| GIT-03 | 单个 PR 的 diff ≤ 400 行（生成代码/迁移/锁文件除外），且必填「变更说明、影响面、回滚方式」 | 一个 PR 只加场景生成器与其单测 | 一个 PR 改 9 个包共 2 000 行 | C（评审） |

### 6.4 PR 检查项（人工，进模板）

| # | 检查项 | 判据 |
|---|---|---|
| 1 | 变更说明 | 说明「改了什么、为什么、影响哪些包」；缺一项打回 |
| 2 | 影响面 | 是否触碰共享库、契约、迁移；触碰则须列出受影响的镜像或视图 |
| 3 | 回滚方式 | 给出回滚动作（revert 提交 / 反向迁移 / 配置回退），迁移类必须写 |
| 4 | 依赖方向 | 新增 import 是否越界（`shared → 服务`、跨服务 import、`web` 直连库） |
| 5 | 测试 | 新增逻辑须有单测；修 bug 须有能复现原缺陷的用例 |
| 6 | 文档同步 | 契约、字段、错误码变更是否同步到对应设计文档与 `schema_version` |

diff 超过 400 行（生成代码、迁移脚本、依赖锁文件除外）须拆分为多个 PR——不是为了形式，而是超过这个规模后评审者会开始「扫一眼点通过」，评审就失效了。

## 8. 文档与注释规范

### 8.1 什么时候必须写注释

| 场景 | 写什么 | 示例 |
|---|---|---|
| 非直观的常量 | 数值**来源**与单位 | `EPS_M = 0.05  # 机柜最小间隙，见 TAB-DD-51 校验 7` |
| 违反直觉的实现 | **为什么**不按常规写 | `# 不用 ORDER BY：调用方已在窗口内保证有序，排序会多一次 12 万行 sort` |
| 业务规则出处 | 需求/设计编号 | `# FR-M3-04：alarm_level 只允许三级，第四级拒绝` |
| 已知缺陷与规避 | 现象、规避条件、失效条件 | `# 绕过 TDengine 3.3 的 tag 更新限制，升级到 3.4 后移除` |
| 契约字段 | 对应文档与版本 | `# 字段定义见 13-3D场景数据模型 TAB-DD-39` |

### 8.2 禁止的注释

| 禁止 | 为什么 | 检出 |
|---|---|---|
| 变更历史（`# 2026-11-20 张三 修改`） | git 已有完整历史；代码里的历史会与真实历史分叉 | CK-15 |
| 注释掉的代码 | 读的人无法判断是「待恢复」还是「已废弃」，且永不被删除 | CK-15 |
| `@author` / `@date` | 归属由 `git blame` 给出，且会随重构失真 | CK-15 |
| 复述代码（`i += 1  # i 加一`） | 增加阅读量、零信息，且改代码时最容易忘记同步 | 评审 R-01 |
| 与实现不符的注释 | 比没有注释更危险——它会让人信任错误的信息 | 评审 |
| 无责任人的 `TODO` | 无人认领即永久遗留 | CK-15 |

一条判断标准：**注释要解释「为什么」，代码本身已经说明了「是什么」**。若一段代码需要注释才能看懂「在做什么」，正确的动作是改名或拆函数，而不是加注释。

## 论文可引用段落

> 编码规范最容易写成道德宣言：命名要有意义、保持代码整洁。这类句子无法执行，也无法验证。我把它改写成四十四条可判定规则，每条带正例、反例与执行级别：A 级由 CI 阻断，B 级告警后限期修复，C 级进入人工评审。例如禁止在协程里做同步阻塞调用不是风格偏好，而是最难排查的故障模式——一个阻塞调用会让所有接口同时变慢，监控却看不出是哪个依赖出错，因此定为阻断项，并要求跨进程调用显式设置超时。更重要的一步是把架构约束也写成脚本：共享库不得被服务反向依赖、服务之间零 import、依赖图不得成环，用 import-linter 在每次提交时判定。评审的注意力因此被释放出来，只用于机器判不了的四类事：命名是否表达业务语义、异常是否保住上下文、新依赖是否突破内存预算、场景参数是否与现场一致。
