## 1. 为什么要单独出这份说明

P3 名义上是「详细设计」，但实际执行中**改了 11 份已经验收过的上游文档**。这些改动分散在各文档的变更记录里，单看任何一份都看不出全貌，评审时容易被质疑「需求怎么又变了」。

本说明的作用是把这些改动集中交代：**改了什么、为什么改、谁发现的、影响到哪里**。所有改动均已在决策台账留痕（D-31 ~ D-47），可逐条追溯。

## 2. 变更性质分类

P3 的改动不是需求蔓延，全部属于以下三类之一：

| 类型 | 定义 | 本次数量 |
|---|---|---|
| **A 缺陷修正** | 设计推演发现原文自相矛盾或在物理上不成立 | 9 处 |
| **B 口径统一** | 同一事实在不同文档有不同数值或写法 | 4 处 |
| **C 决策落地** | 上游只给了「暂定」，P3 首次给出定值与参数 | 17 条（决策台账） |

> 没有一处是「新增需求」或「扩大范围」。判断依据：所有改动都能追溯到一条已有的 FR / QA / 约束，且不增加系统能力。

## 3. 需求层变更（4 处）

### 3.1 FR-M1-06 补传补齐时长：5 min → 15 min

| 项 | 内容 |
|---|---|
| 原文 | 「模拟单机房断连 30 min（240 点/秒），恢复后 **5 min 内**补齐，丢失条数 = 0」 |
| 改为 | 「恢复后 **15 min 内**补齐（约 480 条/秒，为稳态 1.2 倍）」 |
| 原因 | 43 万条 ÷ 300 s = **1440 条/秒**，是稳态 400 点/秒的 **3.6 倍**；补传与在线流量争同一消费通道，物理上不可达。ATAM 早在 P2 就标为 R-02，但当时未回改需求 |
| 发现者 | P3 接口组（时序图推时延预算时算出） |
| 影响面 | SRS FR-M1-06、QA-AVAIL-05 响应度量、P6 压测判据 |
| 决策号 | D-42 |

### 3.2 QA-AVAIL-05 响应度量同步

「5 min 内补齐」→「15 min 内补齐（约 480 条/秒，稳态 1.2 倍）」。与 3.1 同源，保证场景表与 SRS 一致。

### 3.3 数据字典：Redis 键从「8 类」改为「9 类」

| 项 | 内容 |
|---|---|
| 原文 | 「Redis 中**不存任何不可重建的数据**：8 类键全部可从 PG / TDengine / 事件流重建」 |
| 改为 | 「9 类键中 8 类可重建；第 9 类 `cdcim:sess:*`（会话）不可重建，但丢失仅需重新登录，不构成业务事实丢失」 |
| 原因 | 接口设计引入 `cdcim:sess:*` 后，原「全部可重建」的断言不成立。这句断言是 `allkeys-lru` 策略的依据，不能含糊 |
| 发现者 | P3 接口组（登记待回写项） |
| 决策号 | 随 D-39 批次登记 |

### 3.4 3D 需求说明：坐标轴与原点矛盾

| 项 | 内容 |
|---|---|
| 原文 | 「原点：机房地面**西南角**（x 最小、**z 最大**方向）」＋「`+Z` **向南**」 |
| 改为 | 「原点：x 最小、**z 最小**的墙角」＋「`+Z` **由南向北递增**（场景内 `z ≥ 0`）」 |
| 原因 | 按原文，西南角是 z 最大值点，而 +Z 又指南——两个条件同时成立会让全部机柜坐标 `z < 0`，与 `space_node.pos_z ≥ 0` 的约束直接冲突。3D 场景模型按此会全部生成到机房外 |
| 发现者 | P3 3D 模型组（参数化生成时算爆） |
| 影响面 | 3D 需求说明 TAB-SRS-37/38、场景 JSON、坐标映射 |
| 决策号 | D-43 |

另登记一条非缺陷的暂定值：**机房默认尺寸 `[12.0, 3.2, 32.0]` m**（13 列 × 列距 2.4 m = 31.2 m 进深，原示例 12 m 装不下），待现场实测确认（D-44、3D Q1）。

## 4. 架构层变更（6 处）

### 4.1 TDengine 子表粒度：一设备一表 → 一测点一表（**本次最重要**）

| 项 | 内容 |
|---|---|
| 原方案 | 约 300 张子表（一设备一表），同设备多测点同毫秒上报时，用 `point_seq` 在 `ts` 的**微秒位**加 0~999 偏移错开 |
| 改为 | **2000 张子表（一测点一表）** + 降采样 3 × 2000 = **8000 张**；`PRECISION 'ms'`；`ts` 即原始采样时刻，**不做任何偏移** |
| 否决理由 | 微秒偏移会改动原始时间戳。FR-M1-06 的验收判据是「补传数据时间戳与原始采集时刻一致（**偏差 0**）」，偏移 1 毫秒也是偏移。时间戳是监控系统里最不该被加工的字段，一旦允许加工，后续所有「偏差 0」的承诺都失去依据 |
| 代价与收益 | 元数据 5 MB → 32 MB（占 75 GB 磁盘 0.04%），换来事实不被篡改；TDengine 本身面向百万级子表设计，8000 张无压力 |
| 连带影响 | 「子表行放大系数」6.67 → **1**；180 天原始表 8 点叠加查询由「1.66 亿行 / 8.3 s 超标」降为「2490 万行 / **1.24 s 满足** 3 s 目标」；单次查询磁盘读 132 MB → 20 MB |
| 发现者 | P3 数据库组（提出偏移方案）+ 主智能体（否决） |
| 影响面 | 组件映射表、数据架构 §5.1、容量规划 v0.2、数据库设计 v0.2、E-R 图集 v0.2 |
| 决策号 | D-31 |

> **需要说明的是**：P2 阶段是把「2000 子表」改成「300 子表」的那一次修改，本身就改错了。它按「宽表更省元数据」的直觉下调了子表数，却让一个并不存在的性能问题（8.3 s 超时）浮出水面。本次是改回并给出正确理由。

### 4.2 告警判定输入：消费窗口结果 → 消费样本流 + 窗口状态

| 项 | 内容 |
|---|---|
| 原文 | 逻辑视图组件 #9「消费窗口结果；规则热加载」 |
| 改为 | 「**消费清洗后样本流 + 读 Redis 窗口状态**（不消费窗口结果事件）」 |
| 原因 | 窗口需等 60 s 水位线才关闭，让判定等窗口结果，则判定时延下限就是 60 s，**结构上不可能满足 P99 ≤ 3 s**。这是「看图没问题、一算就崩」的典型 |
| 发现者 | P3 接口组（做时序图时发现因果不可能） |
| 影响面 | 逻辑视图、时序图集、告警引擎实现 |
| 决策号 | D-40 |

### 4.3 权限矩阵：16 功能点 → 19 功能点

新增 `alarm:hold`（检修挂起）、`report:export`（报表导出）、`data:repair`（降采样重算）三个独立权限点。

不并入现有权限点的理由：三者风险性质不同（重算改历史聚合、导出入文件、挂起屏蔽推送）。并入会造成「为了挂起告警而获得改规则权」的隐式提权，而 NFR-SEC-02 的验收判据正是「矩阵 100% 覆盖、逐格核对」。

发现者：P3 接口组（47 个接口中有 3 个找不到权限归属）。决策号 D-39。

### 4.4 补传通道：同一通道 → 独立 topic + 独立限速组

| 项 | 内容 |
|---|---|
| 原文（场景视图 S-2） | 「补传走同一入口，不新增通道」 |
| 改为 | 「复用同一事件 schema，但走独立 topic `telemetry.replay` 与独立限速组」 |
| 原因 | 补传期 480~1440 条/秒叠加在在线流量上，会把在线链路 P99 推到 5 s 以上；而补传本身允许 15 min 内完成，优先级低 |
| 影响面 | 场景视图 S-2、消息契约（13 个 topic）、消费组规划 |
| 决策号 | D-41 |

### 4.5 容量规划 v0.2：随 4.1 重算

子表数、放大系数、扫描行数、查询耗时、读带宽、IOPS 全部按「一测点一表」重算，结论由「原始表 8 点叠加超时」转为「满足目标，余量 1.7 s」。瓶颈排序中「单盘 IO」仍保留，但定量依据改为 20 MB / 160 IOPS，并注明「扫描量降为 1/6.67，但队列争用的延迟性质不变」。

### 4.6 图表编号规范 v1.1：编号作用域明确为「文档内唯一」

起因：ATAM 用 TAB-ARCH-59~92、逻辑视图用 81~88，两处重号。P2 末已修订规范（跨文档引用须带文档名），P3 全面执行 `TAB-DB-` / `TAB-DD-` / `TAB-API-` 分前缀，本阶段未再出现重号。

## 7. 没有变的部分（同样重要）

- **架构风格未变**：仍是「边云协同 + 事件驱动微服务」（ADR-0006），C 方案的四条判据结论不变。
- **ATAM 的 Top8 满足度未变**：15 条走查场景中 10 满足 / 5 有风险的分布不变；S2（聚类参数）因 P3 给出定值而关闭。
- **数据处理架构未变**：仍是简化流式 + 存储层重算（ADR-0007），重算接口在 P3 已落地为 API。
- **AI 旁路与出厂关闭未变**：`AI_EXTERNAL_ENABLED=false` 仍是默认值。

一句话：P3 改的是**参数、口径与局部机制**，没有推翻 P2 的结构性判断。

## 9. 论文可引用段落

> 详细设计阶段最有价值的产出不是那十三份文档，而是它反过来修正了上游的十一份。举一个例子：时序库最初设计为「一设备一张子表」，为规避同设备多测点在同一毫秒写入时的主键冲突，我们打算给时间戳加一个 0 到 999 微秒的序号偏移。这个方案在实现上只需一行代码，看起来无害。但当我们把它和补传功能的验收判据并排放时，问题出现了——那条判据说补传数据的采集时间偏差必须为零，而偏移一微秒也是偏移。时间戳是监控系统里唯一不能被加工的事实，一旦允许为它加偏移，所有关于「数据可信」的承诺都会失去立足点。最终我们推翻了这个方案，改为一测点一张子表，代价是元数据从五兆增加到三十二兆。这个代价不到磁盘的千分之一，而它换回的是数据模型的诚实。这件事让我确认了一个判断：在详细设计阶段，最该警惕的不是「设计不出来」，而是「设计得很顺手但悄悄改了事实」。
