---

## 1. 背景与问题

用户要求：WSL2 + Docker 本地部署真实中间件，**内存按 10 GB 以内规划**。原始方案有 A / B 两档：

- A 档：Redpanda（Kafka 协议兼容，单节点）+ Python 消费者 + TDengine
- B 档：Kafka 集群 + Flink + TDengine

B 档的 Flink 单节点需 2–4 GB 常驻（含 JVM 堆外），叠加 TDengine、Redpanda、微服务与系统开销后，在 8 GB 配额下极易 OOM。同时用户是业余时间推进，基础设施调试时间直接侵蚀备考时间。

---

## 2. 候选方案

| 方案 | 常驻内存（估） | 技术完整性 | 落地风险 | 论文影响 |
|---|---|---|---|---|
| A1 纯 A 档 | 3.0–3.5 GB | 中（无 Flink，流计算用 Python 实现） | 低 | 需解释「为什么不用 Flink」——本身是很好的权衡论述 |
| A2 **A 档 + Flink 按需 profile（采纳）** | 常驻 3.5 GB；拉起 Flink 时 5.5–6.5 GB | 高（需要时可用真 Flink） | 低（Flink 不启动则不影响） | 可同时写「裁剪」与「可扩展」两条论述，且能演示 Lambda 架构 |
| B 全量常驻 | 6.5–8 GB | 高 | 高（日常 OOM、启动慢） | 技术栈对齐但无裁剪论述，反而少了加分点 |

---

## 3. 决策

1. **常驻栈采用 A 档**：Mosquitto（MQTT）→ Redpanda（Kafka 协议）→ Python 微服务（消费者组 + 滑动窗口）→ TDengine（时序）+ PostgreSQL（元数据）+ Redis（缓存）+ Qdrant（向量）→ Nginx/Vue3。
2. **Flink 以 compose profile 形式存在**：`docker compose --profile flink up`，默认不启动；仅用于演示 Lambda 架构的批处理层或录制论文素材。
3. **端口策略**：仅 Web 入口 8080 绑定 `0.0.0.0`，其余绑 `127.0.0.1`。
4. **内存硬限**：每个容器在 compose 中显式声明 `mem_limit`，总额不超过 6 GB，为系统与构建留出 2 GB。

---

## 4. 理由

1. **约束优先**：C-01（8 GB）是硬约束，架构必须在约束内成立；先让系统能稳定跑起来，再谈技术栈完整性。
2. **协议兼容即等价性**：Redpanda 对外是 Kafka 协议（分区、副本、消费者组、位点语义一致），论文中讨论 Kafka 的分区副本与顺序保证时，代码与配置可直接对应，不构成「虚假陈述」。
3. **裁剪本身是加分项**：ATAM 的核心是「识别权衡点」。资源约束下主动裁剪、并说明裁剪对哪些质量属性产生影响，正是「架构决策过程 30%」想看的内容。技术栈全量堆齐反而无从体现取舍。
4. **Flink 按需化兼顾两边**：需要时拉起即可演示真实流处理，日常不占内存，属于「用架构手段调和矛盾」，可写成战术。

---

## 5. 代价与缓解

| 代价 | 缓解 |
|---|---|
| Python 实现的窗口计算性能弱于 Flink | 数据量仅 400 点/秒，Python 单进程足够；用 Redis 存窗口状态，避免全内存膨胀 |
| 无 Flink 的状态后端与事件时间语义的完整能力 | 事件时间用消息内时间戳 + 水位线简版实现；论文中说明「生产环境以 Flink 承担」 |
| Redpanda 单节点无副本，不具备真高可用 | 用「至少一次投递 + 幂等写入 + 快速重启」表达数据不丢；高可用作为生产设计章节 |
| 需要用户理解双轨启动方式 | 在部署手册中给出两条命令；`.env.example` 注释说明 |
