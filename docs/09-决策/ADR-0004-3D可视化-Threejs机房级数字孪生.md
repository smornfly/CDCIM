# ADR-0004　3D 可视化：Three.js 机房级数字孪生

| 项 | 内容 |

| 状态 | 🟡 默认采纳（可推翻） |
| 决策人 | 主智能体（按约束推导），待用户确认 |

---

## 1. 背景与问题

用户要求「使用 Three.js 实现 3D 功能」。在动环监控语境下，3D 的价值是**空间态势感知**：值班人员能一眼看出「哪个机房的哪个位置在升温」，而不是在表格里找设备编号。

约束：无 GPU（集显）、浏览器侧渲染、两台设备配置可能不同、论文需要可量化的性能指标。因此问题不是「做不做 3D」，而是**「做到什么粒度、用什么技术手段让它在集显上跑得动」**。

---

## 2. 候选方案

| 方案 | 粒度 | 渲染手段 | 集显可行性 | 运维价值 | 评价 |
|---|---|---|---|---|---|
| S1 全要素精细建模 | 到 U 位与板卡 | 逐模型加载 | ❌ 三角面超百万，帧率 < 10 fps | 高但过剩 | 否决（X-03） |
| S2 **机房级 + 机柜级（采纳）** | 房间、机柜阵列、空调、管线、告警定位 | InstancedMesh + LOD + 按需加载 | ✅ 目标 ≥ 25 fps | 覆盖 90% 场景 | 采纳 |
| S3 仅 2D 热力图 | 平面网格 | Canvas/ECharts | ✅ 最好 | 中 | 作为降级方案保留 |
| S4 服务端渲染 | 云端渲染推流 | 无 | 依赖服务端 GPU | 高 | 与本地部署矛盾，否决 |

---

## 3. 决策

1. **技术**：Three.js + Vite 构建，与 Vue3 应用同仓、独立路由懒加载，避免拖慢 2D 大屏首屏。
2. **粒度**：机房级（房间壳体、机柜阵列、精密空调、桥架管线）+ 机柜级（面板、状态灯、告警高亮）；**不做 U 位/板卡级**。
3. **性能战术**：
   - `InstancedMesh` 批量渲染同构机柜（120 个机柜压到 1 个 draw call）；
   - LOD 三级（近/中/远），远距离退化为色块；
   - 场景几何用 Draco 压缩，纹理 512 px 以内；
   - 温度热力图用贴图/顶点色更新，**不重建几何**；
   - 数据更新走 WebSocket 增量推送，不轮询整场景。
4. **降级**：帧率持续 < 20 fps（连续 3 s）自动切「简化模式」（关阴影、关管线、降 LOD）；用户可手动切 2D 热力图视图。
5. **数据契约**：场景布局与设备坐标存 PostgreSQL（JSON 字段），前端按 schema 加载；布局与代码解耦，换机房不用改代码。

---

## 4. 理由

1. **约束决定粒度**：无 GPU 环境下，几何复杂度直接换算成帧率。机柜级已能回答「哪里出问题」，板卡级只增加成本不增加决策价值。
2. **实例化是数量级优化**：120 个机柜逐 Mesh 渲染约 120 次 draw call，InstancedMesh 降到 1 次，这是能在集显上跑满 25 fps 的关键。
3. **降级必须内置**：演示现场设备性能未知，能自动降级才敢用；同时「性能战术 + 降级策略」本身就是论文性能属性的标准素材。
4. **与 2D 互补而非替代**：2D 大屏负责趋势与列表（信息密度高），3D 负责空间定位（直观性强），两者切换使用。

---

## 5. 代价与缓解

| 代价 | 缓解 |
|---|---|
| 前端包体积增大（three.js 约 600 KB gzip） | 3D 路由懒加载 + 代码分割，2D 首屏不受影响 |
| 建模工作量大（每个机房布局要配坐标） | 用参数化生成（行列数 + 间距 + 尺寸）自动生成机柜阵列，仅特殊设备手配 |
| 集显帧率不稳定 | 内置性能监测与自动降级；论文中记录实测帧率作为「实施效果」 |
| iOS/低端笔记本可能卡顿 | 提供「纯 2D 模式」开关，作为可用性兜底 |

---

## 6. 影响

- P1 需新增 3D 需求（场景范围、交互、性能指标）。
- P2 需新增前端渲染架构章节，并在 ATAM 中评估「表现力 vs 性能」权衡点。
- P3 需产出 3D 场景数据模型（JSON schema）与坐标体系说明。
- P5 实现，P6 实测帧率写入报告。

---

## 7. 论文用法

- 适用题目：**性能设计、人机交互设计、数字孪生与可视化、Web 前端架构**。
- 论述落点：「3D 不是目的，空间态势感知才是；用实例化渲染与 LOD 把复杂度控制住，并准备降级路径」——体现的是性能战术而非炫技。
