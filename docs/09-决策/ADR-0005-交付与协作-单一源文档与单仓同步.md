# ADR-0005　交付与协作：文档单一源 + 单仓多设备同步

| 项 | 内容 |
|---|---|
| 编号 | CDCIM-ADR-0005 |
| 状态 | ✅ 已确认（同步方式由用户提出多设备需求确定） |
| 决策人 | 用户（多设备）+ 主智能体（文档形态） |
| 影响范围 | 全部文档、图表、跨设备与跨会话协作 |

---

## 1. 背景与问题

两个现实条件决定了协作方式：

1. **多设备**：用户在工作与家庭两台设备上推进，环境同构（WSL2 + Docker），需要双向同步。
2. **跨会话**：智能体不跨会话持久，换设备即换会话，上下文必须落盘。

因此需要回答两个问题：文档与图表用什么形态承载？多设备如何同步、如何避免冲突？

---

## 2. 候选方案

### 2.1 文档与图表形态

| 方案 | 优点 | 缺点 | 评价 |
|---|---|---|---|
| A Word/drawio 二进制 | 排版好、领导看得懂 | 无法 diff、无法评审、冲突不可解、跨设备易丢 | 否决 |
| B **Markdown + Mermaid 源码（采纳）** | 纯文本可 diff、可评审、可版本对比、跨设备无冲突风险 | 复杂版式受限 | 采纳 |
| C 在线文档（腾讯文档等） | 协作方便 | 需联网、版本与代码不同步、离线不可用 | 仅作导出展示用 |
| D Markdown + 图片截图 | 简单 | 图片不可维护、不可重生成 | 否决 |

### 2.2 同步方式

| 方案 | 优点 | 缺点 | 评价 |
|---|---|---|---|
| A **单一 GitHub 私有库（采纳）** | 免费、可离线、有历史、有 tag | 需网络推送 | 采纳 |
| B 网盘同步目录 | 无需 git | 冲突产生 `冲突副本` 文件，灾难 | 否决 |
| C 自建 Gitea | 完全可控 | 需额外运维，浪费时间 | 不必要 |

---

## 3. 决策

1. **文档单一源**：全部文档为 Markdown，图表为 Mermaid 源码；导出 SVG/PNG 放 `docs/assets/` 作为派生产物，源始终在 md 内。
2. **仓库**：`git@github.com:smornfly/CDCIM.git`，单分支 `main`，阶段验收通过后打 tag（`p0-baseline` … `p7-thesis`）。
3. **同步纪律**：开工前 `git pull --rebase`，收工前提交推送，不留跨天未提交改动。
4. **环境差异外置**：端口、内存配额、API Key 全部走 `.env`；compose 与脚本禁止绝对路径与硬编码端口。
5. **行尾统一 LF**（`.gitattributes`）、编码 UTF-8（`.editorconfig`）。
6. **状态落盘**：`docs/00-项目状态与门禁.md` + 决策台账作为跨会话交接载体，任何新会话先读它。
7. **论文导出**：需要 Word 版本时，从 Markdown 转 docx（P6/P7 处理），不在写作期维护两份。

---

## 4. 理由

1. **可评审性优先**：文档的最大价值是被审阅与修改，纯文本的 diff 能力不可替代；图片与二进制让评审退化为「看一眼」。
2. **冲突可解**：多设备场景下，纯文本冲突可以手工合并；二进制冲突只能二选一，等于丢工作。
3. **git 即备份**：设备损坏时 `clone` 即可恢复，文档与决策不丢；这比网盘同步更可靠。
4. **单一源避免双维护**：一份 Markdown 同时服务工程文档与论文素材，不产生「文档里一套、论文里一套」的口径分裂——这正是论文真实性最容易翻车的地方。

---

## 5. 代价与缓解

| 代价 | 缓解 |
|---|---|
| Markdown 排版不如 Word 精美 | 交付评审需要时用 Pandoc/脚本转 docx；平时以内容为主 |
| Mermaid 表达复杂图受限 | 规范中允许例外：确实无法表达时用 drawio，但必须提交源文件 |
| 推送需网络 | 本地 commit 可离线，累计后一次推送 |
| 中文文件名在部分工具下麻烦 | 脚本中引用一律加引号；已在规范中明确 |
