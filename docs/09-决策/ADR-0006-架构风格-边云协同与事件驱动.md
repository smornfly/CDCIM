## 1. 背景与问题

系统需要在 8 GB 内存、无 GPU、单机 Docker 的约束下，同时满足：告警判定 P99 ≤ 3 s、年可用性 99.99%、断网 30 min 数据不丢、AI 可降级、三年内可扩展至万级测点。

风格选择不是「哪个先进」，而是「哪个能在这些约束下同时满足 Top8 质量属性场景」。

---

## 2. 候选与评分

| 候选 | 风格 | 加权总分 | Top8 满足度 |
|---|---|---|---|
| A | 分层单体 + 消息队列 | 3.28 | 4✔ 4△ |
| B | 事件驱动微服务 | 4.10 | 7✔ 1△ |
| **C** | **边云协同 + 事件驱动** | **4.22** | **8✔** |
| D | 管道-过滤器（Lambda） | 3.08 | 4✔ 3△ 1✘ |

> 评分为 8 维加权（架构风格纯度 / 可用性 / 性能 / 可修改性 / 可测试性 / 落地成本 / 单机可行性 / 论文可论述性），权重来源与逐项理由见候选对比第 5 节。安全性维度因四候选战术相同（均为 TLS + RBAC + 审计链）而被显式剔除，剔除理由可核查。

C 与 B 仅差 0.12，按预设规则（分差 < 0.2 视为同档）由 Top8 满足度决胜：**唯一全 ✔ 的是 C**。

---

## 3. 决策

采用 **C：边云协同 + 事件驱动微服务**。

具体形态：

- **边缘侧**：采集网关 + 本地磁盘缓冲（独立容器），断网时自治、恢复后补传；
- **中心侧**：按业务能力划分服务（采集接入 / 流计算 / 告警研判 / 联动 / 查询 BFF / AI 旁路），事件总线（Redpanda）异步通信；
- **智能层**：旁路，不参与主链路（ADR-0003）；
- **物理部署**：全部容器运行于同一 WSL2 宿主。

---

## 4. 理由

1. **唯一满足全部 Top8 场景**。真正拉开差距的是两条可用性场景：QA-AVAIL-05（单机房断网 30 min 补传）与 QA-AVAIL-01（总线崩溃自愈）。分层单体 A 与管道 D 在这两条上均为 △ 或 ✘——它们没有「边缘自治」这个结构性手段，只能靠进程重启，无法在断网时保住数据。
2. **与既有决策同向，不推翻前提**。ADR-0002 已选定「MQTT → Redpanda → Python 微服务」的技术栈，C 是在其上的自然延伸；选 A 反而要拆掉消息总线。
3. **零边际成本**。C 与 B 的落地估算同为 42 人日，断网自治能力是「架构形态顺带带来的」，不需要额外开发投入。
4. **论文可论述性最强**。「边云协同」有明确的考点对应（边缘计算、数据同步、最终一致性），比泛泛的「微服务」更能体现取舍。

---

## 5. 代价与缓解

| 代价 | 说明 | 缓解 |
|---|---|---|
| **伪边缘质疑** | 边端与中心在同一台物理机上，「边缘」是否只是逻辑划分？ | ① 边端独立成容器，用 `docker network` 隔离，断网用真实网络隔离验证而非模拟（D-25）；② 论文中如实说明「原型为单机，边缘为逻辑边界，但断网自治行为可被真实验证」 |
| 双端契约漂移 | 边端与中心各自演进，消息 schema 易不一致 | 契约先行（P3 产出消息契约），版本号纳入消息头，消费端做向后兼容 |
| 部署单元多 | 14 个容器，启动顺序与依赖复杂 | compose 用 `depends_on` + healthcheck；启动脚本编排；P4 专门出部署手册 |
| 单点风险 | 单机部署，宿主故障即全停 | 定位为原型环境；生产按集群规划（P2 容量章节），高可用设计另述 |

## 6. 关于「单机部署是否算微服务」的正面回答

这是本文最容易被追问的点，结论是：**算，但只满足四条判据中的三条**。

| 微服务判据 | 本项目 | 说明 |
|---|---|---|
| 独立业务边界（限界上下文） | ✅ | 采集 / 计算 / 告警 / 联动 / 查询 / AI 六个上下文，各自的领域模型不共享 |
| 独立数据所有权 | ✅ | 各服务只写自己的表，跨服务只读视图或事件，不跨库事务 |
| 异步通信与故障隔离 | ✅ | 事件总线解耦，单服务崩溃不影响告警主链路 |
| **独立伸缩（按服务扩副本）** | ❌ | 受 C-01（8 GB）压制，无法按服务独立扩容 |

第四条不成立是**资源约束的结果，不是架构选择的缺陷**。替代手段是「独立重启 + 独立降级」：单服务崩溃只重启该容器，AI 服务可整体停用而不影响主链路。

迁移论证：从单机迁到集群时，**5 项不需要改动**（业务代码、领域模型、消息契约、数据模型、接口），**4 项需要改动且集中在部署运维层**（副本数、服务发现、配置中心、日志聚合）。判断标准很清晰：如果迁移要重写业务代码，那就不是微服务；如果只改部署描述，那服务边界是真的。

---

## 7. 论文用法

- 适用题目：**架构风格选择、微服务架构、边云协同、高可用设计**。
- 论述落点：「四个候选用同一套权重打分，最高分只领先 0.12，最后靠 Top8 场景满足度决胜」——这个过程本身就是「架构决策过程 30%」想要的东西。
- 反面提醒：论文里不要写「我们采用了先进的微服务架构」，而应写「在资源约束下，我们接受了四条判据中的三条，并用独立重启替代独立伸缩」。
