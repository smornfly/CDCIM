# ADR-0001　阶段划分：文档先行的八阶段模型

| 项 | 内容 |
|---|---|
| 编号 | CDCIM-ADR-0001 |
| 状态 | ✅ 已确认（2026-11-11） |
| 决策人 | 用户（孙飞） |
| 影响范围 | 全部阶段、全部文档、排期 |

---

## 1. 背景与问题

项目有双重目标：交付可运行系统 + 产出软考架构设计师论文素材。最初方案（v1/v3 早期）是「设计—实现交替推进」的六阶段（P0–P6），即每个阶段既有设计产出也有代码产出。

用户在 2026-11-11 明确提出新约束：**「项目开工前需要先整理文档，包括开发软件的全生命周期文档，例如需求文档、接口文档、E-R 图、类图、流程图等等，要尽可能详细」**，且「一切都要参照软考高级系统架构师论文中的要求进行」。

问题因此变为：文档是「边做边补」，还是「先成体系再动代码」？

---

## 2. 候选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 交替推进（原 P0–P6） | 每阶段设计+实现并行 | 早期可见效果，反馈快 | 文档易沦为事后补记；需求变更时设计文档与代码脱节；论文素材碎片化 |
| B **文档先行八阶段（采纳）** | P0–P3 纯文档，P4 起才写代码 | 文档天然完整、可评审；架构决策在编码前定型；论文素材成体系 | 前 10 周无可见系统；需求若变动返工成本集中在前段 |
| C 先写论文后做系统 | 先按论文七段式成文，再实现补数据 | 论文最快成型 | 严重违反真实性红线——先有结论后凑过程，评审一眼看穿 |

---

## 3. 决策

采用 **方案 B**，阶段划分调整为：

| 阶段 | 内容 | 代码 |
|---|---|---|
| P0 | 立项与基线（背景、可行性、管理、风险、约束、规范、决策） | 否 |
| P1 | 需求工程（BRD、SRS、用例、质量属性场景、效用树、RTM） | 否 |
| P2 | 架构设计（选型对比、ATAM、4+1 视图、拆分、数据/安全/AI 架构） | 否 |
| P3 | 详细设计（E-R、类图、时序、状态机、接口契约、算法设计） | 否 |
| P4 | 工程骨架与部署（compose、采集、接入、存储链路） | 是 |
| P5 | 全链路功能（流计算、告警、AI 旁路、3D、故障注入） | 是 |
| P6 | 测试与交付（测试、实测报告、部署/运维/用户手册） | 是 |
| P7 | 论文成稿（素材库、草稿、一题多练） | 否 |

并保留门禁协议：每阶段交付后停下等用户验收，未确认不得跨阶段。

---

## 4. 理由

1. **符合评审对「架构师工作流」的期待**。论文的叙事主线是「背景 → 需求 → 选型 → 设计 → 实施 → 效果 → 总结」，文档先行正好与之同构，写论文时几乎是把已有文档重排而非重新创作。
2. **降低真实项目的返工成本**。E-R 图、类图、接口契约若在编码后补，必然「照代码画图」，失去设计价值；先出契约再实现，代码是对设计的验证，这个顺序才能产出真的有决策内容的段落。
3. **满足多设备、碎片时间推进的现实**。文档阶段的任务边界清晰、可拆分、可并行派发子智能体，适合业余时间推进；写代码则要求连续的环境与注意力。
4. **论文素材的完整性依赖前置文档**。评分权重中「架构决策过程 30%」要求写出候选方案与权衡，这些内容只有在设计阶段成体系记录才拿得到分。

---

## 5. 代价与缓解

| 代价 | 缓解措施 |
|---|---|
| 前十周（约 10 周）没有可运行系统，成就感低 | P0–P3 每阶段都有可见文档产出与验收节点；P3 结束后即可看到完整设计蓝图 |
| 需求若在 P4 后变更，前段文档需返工 | 每阶段门禁处做一次「需求稳定性检查」；变更走决策台账 + ADR，控制返工范围 |
| 文档量大约 60 份，存在写成「文档工程」的风险 | 明确「文档服务于两个用途：指导实现 + 论文素材」；凡不服务这两者的文档不写 |

---

## 6. 影响

- 排期：31 周 + 2 个缓冲周（见[项目管理计划](../01-立项/03-项目管理计划.md)）。
- 交付物清单：从 31 项扩至约 62 项（见[文档总目录](../README.md)）。
- 风险登记：新增「文档与实现脱节」风险（R-16）与「范围蔓延」风险（R-17）。

---

## 7. 论文用法

- 适用题目：**软件架构设计、系统开发过程管理、需求工程**。
- 论述落点：「为什么先做架构设计文档再做实现」——可写成过程决策的权衡，而不是简单罗列阶段。
