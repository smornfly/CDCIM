## 1. 背景与问题

时序数据的处理有三种典型形态：Lambda（批流分离）、Kappa（单一流 + 消息重放）、以及简化的单流式。本项目还要处理一个特殊需求：**降采样聚合值与原始明细重算的误差必须 ≤ 0.5%**（FR-M2-03）。这条要求直接约束了「批与流是否允许各写一套聚合逻辑」。

---

## 2. 候选与判定

| 方案 | 结构 | 关键障碍 | 判定 |
|---|---|---|---|
| Lambda | 实时层（流）+ 批层（定时重算），两套代码 | **两套聚合实现必然漂移**，与 0.5% 误差承诺冲突；Flink 批层常驻 2–4 GB，8 GB 下无位置 | ✘ 否决 |
| Kappa | 单一流，靠消息重放支持重算 | 重放需保留 ≥30 天原始消息，约 66 GB，与磁盘预算冲突 | ✘ 否决 |
| **简化流式 + 存储层重算** | 单条实时链路；重算读时序库历史数据，复用同一聚合函数库 | 重算有延迟（非实时）；窗口内不可重放 | ✅ 采纳 |

---

## 3. 决策

1. **只有一条实时链路**：采集 → MQTT → 总线 → 流式计算 → 时序库，降采样在流内完成。
2. **重算不在消息层，在存储层**：需要修正历史聚合时，用 Python 定时任务从 TDengine 读取原始明细，调用**与流计算同一套聚合函数库**重算，整段覆盖写入。
3. **Flink 不进 SLA 路径**：仅以 compose profile 按需拉起，用于演示与论文素材，日常不启动。
4. **误差承诺的实现方式**：不是靠「批流对齐」，而是靠**同一份代码**——流与重算调用同一函数，误差来源只剩浮点累加顺序，可控制在 0.5% 内。

---

## 4. 理由

1. **误差承诺优先于架构范式**。Lambda 的问题不是「重」，而是「同一指标有两份实现」。任何两份代码都会漂移，靠测试对齐只能延缓不能根除。选简化流式，把「一致性」从工程纪律问题变成结构问题。
2. **资源约束是硬门槛**。Flink 单节点常驻 2–4 GB（含 JVM 堆外），叠加 TDengine 与微服务后在 8 GB 配额下必然 OOM。这不是调优能解决的。
3. **Kappa 的正确性依赖买不起的前提**。消息留存 30 天 ≈ 66 GB 未压缩，与 50 GB 级磁盘预算直接冲突。Kappa 在理论上优雅，在预算内不成立。
4. **降采样只是聚合，不需要全量重放**。本项目的「重算」场景是口径变更（例如把 avg 改成加权 avg），从原始表重算即可，不需要重放消息流。

---

## 5. 代价与缓解

| 代价 | 说明 | 缓解 |
|---|---|---|
| 无批流分离的「离线全量重算」能力 | 大规模历史重算要走数据库，可能影响在线查询 | 重算任务限速（每秒读点数上限），在低峰执行，与在线查询分时段 |
| 窗口内不可重放 | 消息不长期保留，60 s 窗口内的原始流无法事后回放 | 窗口状态落 Redis + 明细已入库，回放可用「读库重算」近似替代 |
| 重算有延迟 | 口径变更后历史数据不是立即一致 | 重算任务带 `calc_version`，查询端按版本过滤，避免新旧混读 |
| 单链路故障影响面大 | 流计算停 → 降采样停（明细仍入库） | 明细直写不等窗口（双路径写），降采样走异步旁路；流服务崩溃只影响聚合，不影响入库时延 |

---

## 6. 与「P99 ≤ 2 s」的关系（最易被追问）

入库时延由**双路径写**保证：

- **明细路径**：清洗后直写 TDengine，不等窗口关闭；
- **聚合路径**：窗口（60 s 水位线）关闭后异步写降采样表。

因此 60 s 水位线**不会**污染入库时延——入库 P99 ≤ 2 s 只受明细路径约束，聚合延迟只影响「曲线切换到聚合粒度」的时刻。

---

## 7. 论文用法

- 适用题目：**Lambda 与 Kappa 架构、大数据处理、流式计算、数据一致性**。
- 论述落点：「为什么在有 Flink 的选项下选择不用」——因为误差承诺要求单一实现，而这份承诺来自需求而非技术偏好。这是一个「需求反向约束技术选型」的好例子。
- 反面提醒：不要写成「我们简化了架构所以更先进」，而要写「我们放弃了批流分离带来的复盘能力，用存储层重算与 calc_version 弥补」。
