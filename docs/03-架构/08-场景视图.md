## 1. 为什么要单独画场景视图

前四张视图各自成立，但**各自成立不等于拼得起来**。常见的问题是：逻辑视图说某组件负责削峰，进程视图里却没有对应线程模型，物理视图又把它和会 OOM 的组件放同一容器。

场景视图的作用是**挑几条真实路径走一遍**，检查四个视图在同一件事上是否说得通。本文选 5 条，覆盖正常路径、故障路径、降级路径、变更路径，以及一条最容易被忽略的「配置变更」路径。

每条场景的走查格式固定为：逻辑组件 → 进程与并发 → 部署与网络 → 代码模块 → 验证依据。

## 2. 场景 S-1：一条温度告警从产生到值班确认（正常路径）

| 视图 | 走查内容 |
|---|---|
| **逻辑视图** | 采集接入上下文（collector-gateway）→ 流计算上下文（stream-compute）→ 告警研判上下文（alarm-engine）→ 查询服务（api-service）→ 前端大屏 |
| **进程视图** | 采集为 asyncio 协程（1 worker）；流计算消费 `telemetry.raw` 单分区（并行度上限 1）；告警引擎做窗口判定与抑制；api-service 以 SSE 推送 |
| **物理视图** | 采集在 edge-net，其余在 core-net，时序库在 data-net；跨区仅 4 条通道；SSE 从 api-service 经 Nginx 8080 出宿主 |
| **开发视图** | `core/collector`、`core/stream`、`core/alarm`、`core/api`；事件契约在 `shared/contracts` |
| **验证依据** | FR-M3-01/05/11、QA-PERF-06（判定 P99 ≤ 3 s）、UC-06（告警接收与确认） |

**走查结论**：路径通畅。**敏感处**在告警引擎同时承担判定与推送，是全链路最贵的单点（ATAM R-05 已记录）。

**一处刻意设计**：判定链路**不读时序库**，窗口状态放 Redis。因此 TSDB 故障时告警仍能产生——这是「数据库挂了也要能报警」的结构性保证，不是尽力而为。

## 3. 场景 S-2：单机房断网 30 分钟后补传（故障路径）

| 视图 | 走查内容 |
|---|---|
| **逻辑视图** | 采集接入上下文的本地缓冲职责；补传**复用同一事件 schema**，但走独立 topic `telemetry.replay` 与独立限速组（避免补传挤占在线链路 P99，见《消息主题与事件契约》），逻辑上仍是同一入口 |
| **进程视图** | 断连期间采集继续写本地磁盘队列（配额 150 MB，80% 预警）；恢复后按事件时间批量补传，**不优先于在线数据** |
| **物理视图** | 边端独立容器 + edge-net 隔离，断网可通过 `docker network disconnect` 真实验证（D-25） |
| **开发视图** | `core/collector/buffer`（落盘队列）+ `shared/contracts`（补传消息复用同一 schema，带 `replay=true`） |
| **验证依据** | FR-M1-06、QA-AVAIL-05、UC-02 |

**走查结论**：明细路径成立，**但有一个必须写清的边界**：

> 断网 30 min 的数据全部早于 60 s 水位线，补传后**明细一条不少，降采样聚合却不会自动修正**。因此「数据完整率 100%」必须拆成两个口径：
> - **明细完整率 = 100%**（补传保证）
> - **聚合修正率 = 0%**（需事后按 `calc_version` 重算）

这条是 ATAM 走查 S4 时发现的（R-03 / TP-05），在此固化。P3 需在数据修复接口中给出「按时间区间重算降采样」的能力，否则论文里「零丢失」的说法站不住。

## 4. 场景 S-3：大模型与向量库同时不可用（降级路径）

| 视图 | 走查内容 |
|---|---|
| **逻辑视图** | 智能增强上下文整层旁路，结果字段可空；主链路六个上下文不依赖它 |
| **进程视图** | ai-proxy 异步调用、超时 10 s、熔断 5 次/10 min、并发上限 20；结果经事件回写，无同步等待 |
| **物理视图** | ai-proxy 在 core-net，出站 HTTPS 为唯一外部通道；`AI_EXTERNAL_ENABLED=false` 为出厂默认（D-20） |
| **开发视图** | `core/ai`（Provider 适配器 + 策略）；脱敏在 `core/ai/sanitizer`；前端占位组件在 `web/src/components/ai` |
| **验证依据** | FR-M6-03/05、QA-AVAIL-03、UC-17/18 |

**走查结论**：主链路四项（采集/告警/推送/大屏）可用度 100% 由**结构**保证——没有同步调用、没有共享数据库、没有共享线程池。AI 缺失只损失建议质量。

**但要诚实**：判据「整体功能完整度 ≥ 95%」是靠「AI 只占 5% 功能面」这个划分得出的，不是测出来的。这个百分比在 P6 前只能当设计声明。

## 5. 场景 S-4：集显环境下的 3D 降级（性能路径）

| 视图 | 走查内容 |
|---|---|
| **逻辑视图** | 3D 属应用层展示能力，不是独立上下文；与 2D 大屏共享查询服务 |
| **进程视图** | 渲染在浏览器侧完成，服务端零算力；3D 路由懒加载，不阻塞 2D 首屏 |
| **物理视图** | 3D chunk 由 Nginx 静态分发，体积预算 ≤ 800 KB gzip，不计入 2D 首屏 |
| **开发视图** | `web/src/views/room3d`（独立路由 + 动态 import）；场景配置从 PostgreSQL 读取 |
| **验证依据** | FR-M5-03/06、QA-PERF-04、QA-USE-01、UC-13 |

**走查结论**：降级链 L0→L1→L2→L3 与四视图一致，触发条件统一为「连续 3 s 平均 fps < 20 或渲染内存 > 1.5 GB」，与 SRS v0.5 修订一致。

**视图间的一处差异已澄清**：逻辑视图不区分 2D/3D（都是「展示能力」），物理视图却要区分（chunk 体积、加载时机）。这不是矛盾，是关注点不同——逻辑视图关心职责，物理视图关心分发。

## 6. 场景 S-5：新增第 4 类设备协议（变更路径）

| 视图 | 走查内容 |
|---|---|
| **逻辑视图** | 协议适配属采集接入上下文内部；下游（流计算、告警、存储）通过统一事件契约解耦，**不需要知道协议差异** |
| **进程视图** | 新增协议适配器在采集进程内加载，不新增容器、不重启下游 |
| **物理视图** | 设备侧只需可达 edge-net；端口不变 |
| **开发视图** | 只需在 `core/collector/adapters/` 增加一个适配器实现 + 配置项；`shared/contracts` 不变 |
| **验证依据** | FR-M1-09、QA-MOD-01、NFR-MOD-01 |

**走查结论**：变更影响面被限制在**一个目录 + 一份配置**内，符合「可修改性」的战术要求（限制依赖、延迟绑定）。

这条场景是四个视图一致性的最强证据：如果逻辑视图把协议解析放在流计算里，或者开发视图把适配器散落在多个包，这个结论就不成立。

## 7. 视图一致性检查

| # | 检查项 | 结果 |
|---|---|---|
| 1 | 逻辑组件数（22）与进程部署单元（14）不一一对应，是否有说明 | ✅ 已说明：多个逻辑组件合并进同一容器（如 link-service 并入 alarm-engine，D-30） |
| 2 | 并发模型与「单分区」约束是否同步到物理视图 | ✅ 一致：`telemetry.raw` 单分区，故所有消费类业务单元 worker = 1 |
| 3 | 内存预算三处是否一致 | ✅ 统一为 3 854 MB / 8 GB 配额 47%，余量 4.24 GiB（进程视图与物理视图同源） |
| 4 | 端口绑定策略是否一致 | ✅ 仅 Web 8080 绑 0.0.0.0，其余 127.0.0.1 |
| 5 | 3D 帧率阈值是否唯一 | ✅ 20 fps / 3 s（SRS v0.5 修订后唯一） |
| 6 | 断连缓冲容量三处是否一致 | ✅ 150 MB（P1 修正 + 单机房 240 点/秒基数，D-27） |
| 7 | 计算与告警是否同容器 | ✅ 已拆分（D-29），物理视图按 14 单元部署 |

**遗留差异（已登记，不影响视图成立）**

| 项 | 差异 | 处理 |
|---|---|---|
| 磁盘预算 | 可行性分析 50 GB vs 数据架构 75 GB 预留 | 取 75 GB（含增长余量），可行性分析的 50 GB 为「最低装得下」口径；P4 部署前按 75 GB 准备 |
| 3.87 GB vs 3854 MB | 十进制 GB 与 MB 混用 | 统一按 MB 表述，换算 3.76 GiB |

## 8. 走查带来的两条修正建议

1. **P3 必须补「降采样重算」接口**。S-2 暴露的聚合修正率为 0，不是 bug 而是当前设计的边界；若 P3 不补，运维只能手工刷数。
2. **告警引擎是最贵单点**（同时判定与推送）。若 P6 压测发现它成为瓶颈，第一手段是把推送拆出为独立轻量服务，而不是加副本（受单分区限制，加副本无效）。

## 论文可引用段落

> 本段适用于「系统架构设计」「架构评估」类论文的架构描述部分。
>
> 完成逻辑、开发、进程、物理四张视图后，我没有直接进入详细设计，而是选了五条路径把四个视图走了一遍：一条正常的告警确认链路、一条单机房断网 30 分钟的故障链路、一条大模型不可用的降级链路、一条集显环境下的 3D 性能链路，以及一条新增设备协议的变更链路。走查的价值在第五天显现出来——断网补传那条路径暴露出一个此前被忽略的事实：补传能保证明细一条不少，但降采样聚合不会自动修正，因为补传数据的时间戳全部早于流计算的 60 秒水位线。这意味着我们此前在需求里写的「数据零丢失」是有歧义的，必须拆成明细完整率与聚合修正率两个口径。我把这条写进了场景视图，并要求详细设计阶段补一个按时间区间重算降采样的接口。我的体会是，架构视图最容易犯的错误不是画错，而是四张图各自成立却拼不起来；而检验它们能否拼起来的唯一办法，就是拿真实路径去走。
