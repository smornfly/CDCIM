## 1. 文档目的与使用说明

### 1.1 目的

本文把 SRS 第 6 节的 10 项数据实体（DE-01 ~ DE-10）与 2 类派生数据（降采样、能效指标）展开为**字段级、可实施**的定义，解决三件事：

1. **消歧**：同一概念在不同模块中叫法不同（如「告警级别」在三处出现三种写法），本文给出唯一码值；
2. **对齐**：四类存储（TDengine / PostgreSQL / Redis / Qdrant）各承担哪部分字段，边界写死在本文，避免 P3 出现「同一字段两个库都有、以谁为准」的争议；
3. **可算**：容量、索引、分区所需的信息（单条大小、增长速率、查询模式）在本文一次性给全，P3 只需按图施工。

### 1.2 使用说明

| 读者 | 怎么用本文 |
|---|---|
| 详细设计（P3） | 以 §4 字段表直接生成 DDL；以每节的「主键 / 索引 / 分区」小节生成索引与分区语句；E-R 图以 §3.2 的联系基数为准 |
| 开发（P5） | 以 §5 枚举字典写代码常量，禁止在代码中硬编码中文字面量；以 §6 质量规则写校验逻辑 |
| 测试（P6） | 以 §5 枚举与 §6 质量规则构造边界用例；以 §7 容量表核对数据量 |
| 论文（P7） | 以 §3 实体总览、§4.4 时序建模、§8 血缘表作为「数据架构」段素材 |

### 1.3 三处不写

- **不写 DDL**：`CREATE TABLE` 属 P3，本文只给类型与约束意图；
- **不写接口报文**：字段如何组装成 JSON 属 P3 接口契约；
- **不写实测值**：容量全部标注「估算」，索引效果不承诺提升比例。

## 2. 命名规范

### 2.1 总体风格

| 对象 | 规则 | 示例 |
|---|---|---|
| 库 / Schema | PostgreSQL 用 `cdcim`；TDengine 用 `dcim`；Qdrant 用默认库 | `cdcim.point_def` |
| 表名 | 全小写 `snake_case`，**单数**，不加 `tbl_` 前缀，长度 ≤ 32 字符 | `alarm_event` |
| 字段名 | 全小写 `snake_case`，不用缩写（行业通用缩写除外：`id`、`ts`、`ip`、`uri`） | `first_occur_at` |
| 索引名 | `idx_<表名>_<列名简写>`；唯一索引 `uk_`；主键 `pk_`；BRIN `brin_`；GIN `gin_` | `idx_raw_alarm_device_ts` |
| 约束名 | `ck_<表名>_<语义>`；外键 `fk_<表名>_<引用表>` | `ck_alarm_event_level` |
| 分区名 | `p_<表名>_<yyyymm>`（月分区）/ `p_<表名>_<yyyy>`（年分区） | `p_raw_alarm_202611` |
| 子表名（TDengine） | `t_<device_code 小写化，非字母数字转下划线>` | `t_ups_a01` |
| 超级表（TDengine） | `st_<语义>`，降采样加粒度后缀 | `st_metric_1m` |
| Qdrant collection | `kb_<用途>` | `kb_docs` |
| Redis key | `cdcim:<域>:<对象>:<标识>`，冒号分隔，全小写 | `cdcim:sup:rule_1021:dev_33:pt_7` |

### 2.2 表名语义后缀约定

不使用「前缀分类」（`dim_` / `fact_`）的原因：本系统实体数少（23 张表），前缀会让 `device` 变成 `dim_device`，与 SRS 实体名脱节，反而增加追溯成本。改用**后缀表达数据性质**：

| 后缀 | 含义 | 实例 |
|---|---|---|
| `_def` | 定义类主数据（相对稳定、被引用） | `point_def` |
| （无后缀） | 主数据主体 | `device`、`space_node`、`role` |
| `_rule` | 配置类规则 | `alarm_rule` |
| `_event` | 聚类/聚合后的事件 | `alarm_event` |
| `_record` | 一次操作的执行记录 | `linkage_record` |
| `_log` | 只追加日志 | `audit_log` |
| `_link` | 关系/关联表 | `topology_link`、`ticket_link` |
| `_daily` | 日粒度派生汇总 | `energy_metric_daily` |

### 2.3 主键与外键

| 规则 | 说明 |
|---|---|
| 代理主键 | 单表主键统一 `<表名单数>_id`，类型 `bigint`（`GENERATED ALWAYS AS IDENTITY`），**不用自然键做主键** |
| 业务唯一键 | 每张主数据表必须有 1 个业务唯一键（`*_code`），加 `uk_` 唯一索引，供人工检索与外部系统对接 |
| 外键命名 | `<被引用表名单数>_id`，如 `device_id`、`space_node_id` |
| 外键策略 | 台账类外键 `ON DELETE RESTRICT`（禁止删除被引用对象，改用 `lifecycle_status` 退役）；日志/事件类**不建物理外键**（避免写放大与历史数据耦合） |
| 联合主键 | 仅用于关联表（`user_role`、`role_permission`）与派生汇总表（含 `stat_date`） |

### 2.4 字段命名细则

| 语义 | 命名模式 | 类型 | 示例 |
|---|---|---|---|
| 时刻（绝对时间） | `*_at` | `timestamptz(3)` | `ack_at`、`created_at` |
| 日期（日粒度） | `*_date` | `date` | `stat_date`、`install_date` |
| 时长（秒） | `*_s` | `smallint` / `int` | `duration_s`、`escalate_interval_s` |
| 时延（毫秒） | `*_ms` | `int` | `execute_latency_ms` |
| 布尔 | `is_*` / `has_*` / `*_enabled` / `*_flag` | `boolean` | `is_suppressed`、`parent_suppress_enabled` |
| 计数值 | `*_count` | `int` / `bigint` | `suppressed_count` |
| 测量值 | `val_*` 或 `*_value` | `numeric(18,6)` / `double` | `val_avg`、`threshold_value` |
| 枚举 | 语义名 + 英文存储值 | `varchar(16~32)` 或 `smallint` | `alarm_level='critical'` |
| 扩展字段 | `*_ext` / `params` | `jsonb`（必须含 `schema_version`） | `protocol_params` |
| 版本号（乐观锁） | `row_version` | `int`，每次更新 +1 | — |

### 2.5 禁止项

- 禁止中文列名、拼音列名、`col1/col2` 类无意义名；
- 禁止用 `type`、`status`、`level` 作为裸列名（保留字与歧义），必须带语义前缀：`device_type`、`alarm_level`；
- 禁止同一个含义出现两种类型（如「设备编号」一处 `varchar` 一处 `bigint`）；
- 禁止在枚举列存中文（如 `alarm_level='紧急'`），中文只出现在展示层映射表。

### 3.2 实体联系与基数（E-R 逻辑视图）

| 联系 | 基数 | 说明 | 落地方式 |
|---|---|---|---|
| 设备 — 测点 | 1 : N | 一台设备挂多个测点，一个测点只属一台设备 | `point_def.device_id` |
| 空间节点 — 空间节点 | 1 : N（自关联） | 机房 → 列 → 机柜 → U 位，四层 | `space_node.parent_node_id` |
| 空间节点 — 设备 | 1 : N | 一台设备安装在一个机柜（或 U 位） | `device.space_node_id` |
| 设备 — 设备 | 1 : N（自关联） | 供电/网络上游关系（UPS → 列头柜 → 机柜 PDU） | `device.parent_device_id` |
| 拓扑关系 — 任意节点 | N : N（多态） | 电气链、网络链、制冷链，跨越空间与设备两类节点 | `topology_link`（`src_node_type` + `src_node_id`） |
| 设备 — 时序子表 | 1 : 1 | 一台设备一张 TDengine 子表 | `t_<device_code>` |
| 测点 — 时序记录 | 1 : N | 一个测点产生多条时序记录 | `st_metric.point_id`（列，非 TAG，理由见 §4.5） |
| 告警规则 — 原始告警 | 1 : N | 一条规则可命中多次 | `raw_alarm.rule_id` |
| 告警事件 — 原始告警 | 1 : N | 一个事件吸收多条原始告警；原始告警可能未被聚类（`event_id` 为空） | `raw_alarm.event_id`（可空） |
| 告警事件 — 联动记录 | 1 : N | 一个事件可触发多次联动（门禁 + 抓拍） | `linkage_record.event_id` |
| 告警事件 — 工单 | 1 : 0..1 | 一个事件最多关联一张主工单 | `ticket_link.event_id` 唯一约束（按主单） |
| 知识库条目 — 向量切片 | 1 : N | 一篇文档切 10 ~ 200 个 chunk | `kb_docs.payload.kb_id` |
| 用户 — 角色 | N : M | 一人可多角色（值班员兼工程师场景禁止，见约束） | `user_role` |
| 角色 — 权限 | N : M | 一个角色含多个权限点 | `role_permission` |
| 用户 — 审计日志 | 1 : N | 审计记录操作人快照，不随用户改名变化 | `audit_log.actor_id` + `actor_name` 快照 |
| 机房 — 能效日指标 | 1 : N | 每机房每日每指标一行 | `energy_metric_daily.room_id` + `stat_date` |

**三处刻意不建联系**：

1. `raw_alarm` 与 `st_metric` 之间**不建外键、不做关联查询**——跨库（PG ↔ TDengine）无分布式事务，靠 `trace_id` 与「设备 + 测点 + 时间窗」在应用层关联，这是 §8 血缘表的显式约定；
2. `audit_log` 与 `user_account` 之间**不建外键**——用户被删除（实际是禁用）后审计记录必须仍可追溯，故存 `actor_id` + `actor_name` 双份；
3. `topology_link` **不建到两张表的物理外键**——多态引用（可能指向 `space_node` 或 `device`），改由应用层校验 + 每日一致性巡检。

## 4. 字段级数据字典

> 字段表列含义：**数据类型**按 PostgreSQL 写，TDengine 对应类型在 §4.4 单独列出；**长度/精度**对 `varchar` 指字符数，对 `numeric` 指 `(p,s)`；**必填**指 `NOT NULL` 且无默认值时必须显式赋值。

### 4.1 测点定义 `point_def`（主数据，22 字段）

| 字段名 | 中文名 | 数据类型 | 长度/精度 | 必填 | 默认值 | 取值范围/枚举 | 说明 |
|---|---|---|---|---|---|---|---|
| point_id | 测点主键 | bigint | — | 是 | 自增 | > 0 | 代理主键，TDengine 中以列形式冗余存储 |
| point_code | 测点编码 | varchar | 64 | 是 | 无 | `^[A-Z0-9_-]{4,64}$` | 业务唯一键，约定 `<设备编码>-<物理量>-<相/路>` |
| device_id | 所属设备 | bigint | — | 是 | 无 | 引用 `device.device_id` | 一测点只属一台设备 |
| point_name | 测点名称 | varchar | 128 | 是 | 无 | 非空 | 展示名，如「A 相输入电压」 |
| point_type | 测点类型 | varchar | 16 | 是 | 无 | E3 | analog / discrete / accumulate / text |
| data_type | 寄存器数据类型 | varchar | 16 | 是 | `uint16` | E3a | uint16 / int16 / uint32 / int32 / float32 / bool / string |
| unit | 工程单位 | varchar | 16 | 否 | `NULL` | 见 §6.5 单位表 | 统一 SI 词头，如 `V`、`A`、`kW`、`℃`、`kWh` |
| register_addr | 采集地址 | varchar | 64 | 是 | 无 | 非空 | Modbus 寄存器号 / SNMP OID / MQTT 主题路径 |
| function_code | 功能码 | smallint | — | 否 | `NULL` | 1/2/3/4 | 仅 Modbus 有效；SNMP/MQTT 为空 |
| scale_factor | 换算系数 | numeric | (12,6) | 是 | `1.000000` | > 0 | 原始值 × 系数 + 偏移 = 工程值 |
| offset_value | 换算偏移 | numeric | (12,6) | 是 | `0.000000` | 任意 | 同上 |
| deadband | 死区 | numeric | (12,6) | 是 | `0.005000` | ≥ 0 | 相对量程比例，默认 0.5%；0 表示不过滤 |
| sample_interval_s | 采集间隔 | smallint | — | 是 | `5` | 5 / 30 | 快变 5 s，慢变 30 s |
| range_min | 量程下限 | numeric | (18,6) | 否 | `NULL` | 任意 | 超量程判 Uncertain 的依据 |
| range_max | 量程上限 | numeric | (18,6) | 否 | `NULL` | > range_min | 同上 |
| critical_flag | 关键测点标记 | boolean | — | 是 | `false` | true/false | 过载降级时保留的测点（FR-M1-08） |
| default_rule_id | 默认告警规则 | bigint | — | 否 | `NULL` | 引用 `alarm_rule.rule_id` | 建点时预绑，减少配置工作量 |
| point_status | 测点状态 | varchar | 16 | 是 | `enabled` | enabled / disabled / reserved | 停用不删，保留历史可查 |
| remark | 备注 | varchar | 256 | 否 | `NULL` | 任意 | 现场接线说明等 |
| created_at | 创建时间 | timestamptz | (3) | 是 | `now()` | — | UTC 毫秒 |
| updated_at | 更新时间 | timestamptz | (3) | 是 | `now()` | — | UTC 毫秒，触发器维护 |
| updated_by | 更新人 | bigint | — | 否 | `NULL` | 引用 `user_account.user_id` | 导入场景记录导入任务 ID |

**主键** `pk_point_def (point_id)`；**唯一键** `uk_point_def_code (point_code)`。
**索引** `idx_point_def_device (device_id, point_type)`（按设备列测点，最高频查询）、`idx_point_def_rule (default_rule_id)`、`idx_point_def_critical (critical_flag) WHERE critical_flag = true`（部分索引，支撑降级时快速取关键点）。
**分区** 不分区（2 000 行量级，全表常驻内存）。
**说明** 台账变更后通过 `meta.change` 事件广播，消费方 30 s 内生效（FR-M2-09），不做跨服务强一致读。

### 4.2 设备台账 `device`（主数据，25 字段）

| 字段名 | 中文名 | 数据类型 | 长度/精度 | 必填 | 默认值 | 取值范围/枚举 | 说明 |
|---|---|---|---|---|---|---|---|
| device_id | 设备主键 | bigint | — | 是 | 自增 | > 0 | 代理主键 |
| device_code | 设备编码 | varchar | 64 | 是 | 无 | `^[A-Z0-9_-]{3,64}$` | 业务唯一键，同时是 TDengine 子表名来源 |
| device_name | 设备名称 | varchar | 128 | 是 | 无 | 非空 | 如「A 区 1# UPS」 |
| device_type | 设备类型 | varchar | 32 | 是 | 无 | E4 | ups / pdu / battery / precision_ac / th_sensor / leak / smoke / door_ctrl / camera / gateway |
| vendor | 厂商 | varchar | 64 | 否 | `NULL` | 任意 | 如「施耐德」「维谛」 |

### 4.5 测点时序值 `st_metric`（TDengine 超级表）

**建模方式**：1 张超级表（STABLE）+ **按设备一表**的子表（约 300 张），子表名 `t_<device_code 小写化>`。选择「按设备建子表」而非「按测点建子表」的理由：① 设备是台账与拓扑的最小管理单元，子表与 `device` 一一对应，新增设备只需建 1 张子表；② 单设备测点数约 7 个，写入时同一批数据落在同一子表，降低子表数量与元数据开销；③ 按设备查询（「这台 UPS 的所有量」）是最高频的运维动作，单子表扫描最快。

| 字段名 | 中文名 | 数据类型 | 长度/精度 | 必填 | 默认值 | 取值范围/枚举 | 说明 |
|---|---|---|---|---|---|---|---|
| ts | 事件时间 | timestamp | 毫秒 | 是 | 无 | 单调不回退（同设备同测点） | 主键时间列，UTC 毫秒；表内第一列 |
| point_id | 测点 ID | bigint | — | 是 | 无 | > 0 | **普通列（非 TAG）**，原因见下方说明 |
| val_double | 浮点值 | double | — | 否 | `NULL` | IEEE 754 | analog / accumulate 测点使用 |
| val_int | 整型值 | bigint | — | 否 | `NULL` | int64 | 计数类、状态码类 |
| val_bool | 布尔值 | bool | — | 否 | `NULL` | true/false | discrete 测点使用 |
| quality | 质量码 | tinyint | — | 是 | `0` | E14（0/1/2/3） | 随数据持久化，不可为空（FR-M1-05） |
| ts_source | 时间来源 | tinyint | — | 是 | `1` | E15（0/1/2/3） | 设备时钟 / 网关时钟 / 回放 / 补录 |
| raw_val | 原始值 | double | — | 否 | `NULL` | 任意 | 换算前的寄存器值，用于追溯与重算（FR-M2-01） |

| is_late | 迟到标记 | tinyint | — | 是 | `0` | 0 / 1 | 1 表示超 60 s 水位线后到达 |

**TAG（标签）设计**（子表级常量，写入时随子表定义一次，后续只需 `USING ... TAGS` 指定）：

| TAG 名 | 类型 | 取值来源 | 用途 |
|---|---|---|---|
| device_id | bigint | `device.device_id` | 跨子表按设备聚合；与 PG 台账对齐的唯一桥 |
| room_id | int | `space_node.room_id` | 按机房过滤，减少扫描范围（3 机房） |
| rack_id | bigint | `device.space_node_id`（机柜节点） | 按机柜聚合，支撑热力图（FR-M5-05） |
| device_type | varchar(24) | `device.device_type` | 按设备类型批量聚合（同类 UPS 对比） |
| critical_flag | tinyint | `point_def` 汇总的设备级标记 | 降级查询时快速筛关键设备 |

**为什么 `point_id` 不能做 TAG**：TDengine 的 TAG 在同一子表内必须是常量，而本模型一张子表承载一台设备的多个测点，`point_id` 在子表内是变化的，只能作为普通列。若强行把 `point_id` 做 TAG，则必须改为「一测点一子表」（2 000 张），与「按设备建子表」的约定冲突，且设备增删时要批量建删子表。代价是：按单测点查询需在子表内做 `WHERE point_id = ?` 的列过滤，因单设备数据量小（约 7 点 × 17 280 条/天），过滤代价可接受。

**主键** TDengine 以 `(ts)` 为时间主键，**业务幂等键为 `(device_id, point_id, ts)`**：同设备子表内 `(point_id, ts)` 重复写入按「后到覆盖」处理（FR-M2-05），依靠 TDengine 的主键去重语义 + 应用层保证 `ts` 不重复投递。
**索引/加速** 开启 `last_row` 与 `last_value` 缓存，支撑「取最新值」不扫表；标签过滤（`room_id`、`device_type`）走标签索引。
**分区与分片建议**：
- `KEEP 180`（天），`DURATION 10`（每 10 天一个数据文件组，180 天约 18 个时间分片）；
- 生产 3 节点集群 `REPLICA 3`，原型单机 `REPLICA 1`；
- `VGROUPS` 原型 2、生产 6（按 `room_id` 与 `device_type` 的组合做哈希，避免单机房写热点，对应 C-17 的「分区键按机房 + 设备类型」）；
- 写入方式：`INSERT INTO t_xxx USING st_metric TAGS (...) VALUES (...)`，批量 500 条或 200 ms 攒批（组件映射表 §5.1）；
- 子表在设备台账新增时由 stream-compute 懒创建（`CREATE TABLE IF NOT EXISTS`），台账删除只停写不删表（保留历史）。

**分区** 按月 `RANGE (created_at)`，保留 16 个月（1 年配置 + 4 个月缓冲），超期分区整块归档后 `DROP`。
**只追加的强制手段**：
1. 应用层：审计写入接口只提供 `INSERT`，无 `UPDATE` / `DELETE` 方法；
2. 数据库层：审计表 owner 与业务账号分离，业务账号仅授予 `INSERT` 与 `SELECT`，**不授予 `UPDATE` / `DELETE` / `TRUNCATE`**；
3. 触发器：`BEFORE UPDATE OR DELETE` 抛异常（双保险，防止误授权的 DBA 操作）；
4. 归档替代删除：超期数据先导出并校验 `record_hash` 链完整，再 `DROP PARTITION`；
5. 任何对审计表的越权尝试本身再记一条 `operation_result = 'denied'` 的审计（FR-M5-13）。
**等保口径** 留存 ≥ 6 个月是**法定最低**（C-10），本期配置 1 年；审计留存期独立于业务数据归档策略，不受原始时序 180 天策略影响。

| `cdcim:ai:cb:{provider}` | STRING（连续失败计数）+ HASH（熔断状态与截止时刻） | 600 s | AI 熔断计数与熔断窗口（ADR-0003：连续失败触发熔断，10 min 内不再调用） | 到期自动失效；调用成功计数清零 |
| `cdcim:ai:cache:{alarm_fingerprint}` | STRING（JSON 建议结果） | 3 600 s | 相同告警模式的建议复用，压降 Token 成本（见 SRS-08 成本章节） | LRU + TTL，命中不写回 |
| `cdcim:cache:point:last:{point_id}` | STRING（value\|ts\|quality） | 60 s | 单点最新值 | LRU |
| `cdcim:ai:quota:{yyyymmdd}` | STRING（计数器） | 25 h | AI 日调用限流（FR-M6-09） | 自然日重置 |

**说明** Redis 中**不存任何不可重建的数据**：8 类键全部可从 PG / TDengine / 事件流重建，故 `maxmemory-policy = allkeys-lru`，`maxmemory 96 MB`（组件映射表 §1.4）。这一约束保证 Redis 丢数据不会造成业务事实丢失，只影响短时判定性能。

## 6. 数据质量规则

### 6.1 时间规则

| 规则 | 要求 | 落地 |
|---|---|---|
| 时间戳精度 | 毫秒；PG 用 `timestamptz(3)`，TDengine 用 `timestamp`（默认毫秒） | 全表统一，禁止 `timestamptz` 无精度声明 |
| 时区 | 存储一律 UTC；展示层按浏览器时区转换 | 禁止存本地时间字符串 |
| 时钟偏差 | 全链路 ≤ 100 ms（NTP 基准）；超 1 s 在数据上标 `quality = uncertain` | 由采集侧判定（IF-EXT-04） |
| 单调性 | 同设备同测点 `ts` 不回退 | 采集侧拦截；TDengine 主键天然拒绝重复 |
| 事件时间 vs 处理时间 | 两者都存（`ts` / `ingest_ts`） | 事件时间用于窗口，处理时间用于时延统计 |

### 6.2 乱序与迟到

| 情形 | 处理 | 落地位置 |
|---|---|---|
| 迟到 ≤ 60 s | 计入原窗口，触发窗口重算，`agg_version + 1` | `st_metric_1m` 覆盖写 |
| 迟到 > 60 s | 写 `telemetry_late_bypass`，不修正已发布聚合 | §4.7 |
| 同键不同值 | `ts_source = device` 优先；否则后到覆盖，并累计覆盖次数 | 写侧比较，不入表 |
| 迟到量监控 | 每分钟统计迟到条数，超阈值产生 `data_delay` 告警 | 监控指标 |

### 6.3 缺失值

- **不插值**：缺失即缺失，聚合按 `valid_count / sample_count` 记录；
- 曲线展示缺失段**断开**，不连线（避免视觉伪造连续）；
- 单测点连续缺失 ≥ 3 个采集周期 → 判定「数据中断」，进入设备离线逻辑；
- 聚合可信判据：有效点占比 ≥ 80% 记 `quality_flag = 0`，否则 1（SRS 6.2.2）。

### 6.4 幂等键一览

| 数据对象 | 幂等键 | 冲突处理 |
|---|---|---|
| 时序值 | `(device_id, point_id, ts)` | 后到覆盖，值与质量码取最新 |
| 原始告警 | `alarm_fingerprint = hash(rule_id, device_id, point_id, window_start)` | 唯一约束拒绝，不产生重复告警 |
| 告警事件 | `event_code` | 由序列生成，天然唯一 |
| 联动指令 | `request_id`（客户端生成） | 24 h 内重复提交只执行 1 次 |
| 迟到旁路 | `(device_id, point_id, ts)` | 覆盖写 |
| 知识库条目 | `content_hash` | 同内容不重复入库、不重复嵌入 |
| 审计日志 | 无幂等键（**必须允许重复记录**，如两次相同查询各记一条） | 不适用 |
| 能效日指标 | `(room_id, stat_date, metric_type, calc_version)` | 重算覆盖 |

### 6.5 单位统一

| 物理量 | 统一单位 | 禁止用法 |
|---|---|---|
| 温度 | `℃` | 华氏度需在采集侧换算后入库 |
| 电压 / 电流 | `V` / `A` | 不允许 kV/mA 直接入库（换算后存） |
| 功率 | `kW` | 不用 W、不用 kVA 混存（视在功率单列测点） |
| 电能 | `kWh` | 累计量，只增不减 |
| 频率 | `Hz` | — |
| 湿度 | `%RH` | — |
| 比率类 | `ratio`（0 ~ 1） | 展示层乘 100 显示为 % |
| 时间 | 秒（`*_s`）/ 毫秒（`*_ms`） | 不用分钟、小时做字段单位 |

单位写入 `point_def.unit`，`scale_factor` 承担换算；同一物理量在同一设备类型下**必须同名同单位**，由导入校验拦截（FR-M1-03）。

### 6.6 取值范围校验

| 校验 | 规则 | 违背后果 |
|---|---|---|
| 量程校验 | `range_min ≤ val ≤ range_max` | 超限置 `quality = uncertain`，不参与聚合 |
| 枚举校验 | 字段值必须属于 §5 定义域 | 写入拒绝（400） |
| 引用完整性 | 台账类外键必须存在 | 写入拒绝（RESTRICT） |
| 状态机校验 | 只允许 §5.2 / §5.9 定义的迁移 | 拒绝（409）+ 审计 |
| 层级校验 | `space_node` 层级不可跳（rack 父必须 row） | 写入拒绝 |
| 环检测 | `device.parent_device_id`、`topology_link` 不得成环 | 写入拒绝 |

### 7.2 三点口径说明

1. **1 min 降采样按 12 GB 而非 SRS 的 16 GB**：SRS 6.3 按 1 600 个模拟量估算得 16 GB，本文按「实际参与降采样的有效模拟量约 1 200 点」估算得 12 GB（与项目背景卡草案一致），二者同量级；规划基数取 12 GB，**上限按 16 GB 预留磁盘**，差异登记见 §9 待确认 1。

## 8. 数据流与血缘

> 一行一条链路。**写入方**为唯一写主体（其他服务只读），**读取方**列出全部消费方。跨库链路不做事务，靠幂等与版本号收敛。

| 数据对象 | 写入方（服务） | 读取方 | 触发方式 | 一致性 / 时延 |
|---|---|---|---|---|

**三条血缘约束**：

1. **单一写主体**：每张表只有一个服务有写权限，避免「双写冲突」；跨服务数据需求走事件或只读副本。
2. **不跨库回查**：alarm-engine 判定时不回查 TDengine（避免把时序库抖动传导到告警链路），窗口状态在 Redis、规则在内存、台账在启动时加载。
3. **AI 只写建议字段**：ai-proxy 对 `alarm_event` 只有 `ai_suggest_*` 四列的更新权限，**无状态字段写权限**，这是「AI 不进主链路」在数据权限层的落点（FR-M6-08）。

## 论文可引用段落

> **【适用题目类型】论数据架构设计 / 论数据库设计 / 论时序数据处理**

在数据架构设计中，我先完成逻辑数据字典再进入物理建表，这一顺序的价值在时序数据上体现得最明显。系统约两千个测点，快变五秒、慢变三十秒，日增三千四百余万条，按关系表建模会因索引膨胀而不可写。因此我采用超级表加子表模型：超级表统一定义列结构，按设备建约三百张子表，机房、机柜、设备类型作为标签。这里有个易被忽略的细节——测点编号不能做标签，因为标签在子表内必须为常量，而一张子表承载一台设备的多个测点，它只能作为普通列；若强行做标签就要退化为两千张子表，元数据与增删成本都会上升。围绕这张表我定了三条治理规则：以设备、测点、时间戳为幂等键，后到覆盖解决重复投递；允许六十秒乱序并触发窗口重算，超窗数据进旁路表而不修正已发布聚合；质量码随数据持久化，缺失不插值。这三条规则使「至少一次投递」在效果上等价于「恰好一次」，而不必引入分布式事务。
