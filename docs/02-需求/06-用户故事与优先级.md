## 1. 文档目的

### 1.1 与 SRS 的关系

SRS 回答「系统应做什么、做到什么程度」，是需求侧对设计与测试的**正式契约**；本文回答「谁为了什么要用、先交付哪一块」，是**交付侧对排期与裁剪的切片**。两者不是重复关系，而是同一批需求在两种视角下的组织方式。

| 维度 | SRS（CDCIM-P1-SRS-01） | 本文（CDCIM-P1-SRS-03） |
|---|---|---|
| 回答的问题 | 系统应做什么、做到什么程度 | 谁为了什么要用、先做哪一块 |
| 组织单位 | 模块 → 功能需求（69 条 FR） | 角色 → 用户故事（34 条 US） |
| 验收形式 | 需求级判据（阈值 + 条件 + 验证方法） | 故事级 Given-When-Then（3 ~ 5 条） |
| 粒度倾向 | 一条 FR 只描述一个行为，可很细 | 一个故事是一个可独立验收的交付单元，可含多条 FR |
| 变更影响 | 改一条 FR 影响架构元素与测试用例 | 改一个故事影响迭代排期与发布批次 |
| 主要用途 | 架构设计、接口设计、测试验收 | 迭代排产、范围裁剪、进度沟通 |

**追溯链**：`BR → FR → US`。反向核对时，以 FR 编号为键把本文与 SRS 对齐；SRS-06 的 RTM 仍以 FR 为主键，本文不另建矩阵，只在第 6 节给出一致性核对表。

### 1.2 读者与使用方式

| 读者 | 用法 |
|---|---|
| 项目本人（兼产品与开发） | 按第 5 节的批次排产；工期不足时按第 7 节的顺序裁剪，不临时拍脑袋 |

| 测试（P6） | 第 4 节每条故事的 Given-When-Then 可直接转为验收用例骨架 |

### 1.3 本文不覆盖

| 不覆盖内容 | 归属 |
|---|---|
| 需求的完整判据与阈值定义 | SRS 第 4 节、第 7 节 |

## 2. 故事编写规则

### 2.1 INVEST 原则的落地方式

INVEST 不是口号，每条都要有可检查的落地动作，否则故事会退化成「模块任务」。

| 字母 | 含义 | 本项目的落地做法 | 违反时的处理 |
|---|---|---|---|
| **I** Independent | 独立 | 每个故事可在 1 个迭代内独立验收；依赖显式写在故事头的「依赖」字段，且**最多 1 层**（不出现 A 等 B、B 等 C 的链） | 出现 2 层依赖即拆故事或调整迭代顺序 |
| **N** Negotiable | 可协商 | 范围可谈（先做哪部分、做多深），**验收判据不可谈**——判据来自 SRS 的 FR，改判据须回 SRS 走变更 | 判据被口头放宽即视为需求变更，记决策台账 |
| **V** Valuable | 有价值 | 每个故事至少关联 1 条 BR，且能说出对 G-1 ~ G-6 中哪一项有贡献 | 说不出价值的故事不进批次，退回需求池 |
| **E** Estimable | 可估算 | 全部给出斐波那契故事点；估不出来的故事说明范围不清，先澄清再估 | 连续两次估不出即拆 |
| **S** Small | 小 | 单故事 ≤ 13 点（≈ 6.5 人日）；13 点故事必须在进入迭代前拆成 2 个执行项 | 超过 13 点强制拆分 |
| **T** Testable | 可测 | 3 ~ 5 条 Given-When-Then，每条含阈值、条数或时间；禁止无判据的「正常可用」 | 见 2.3 的禁用词表 |

**关于 13 点故事的例外说明**：按 3.5 人日/周的节奏，13 点 ≈ 6.5 人日 ≈ 2 周，正好占满一个迭代的一半以上。本文保留 3 个 13 点故事（US-13 降噪、US-18 门禁联动、US-24 3D 场景），理由是它们各自是一个**不可再分的闭环**（降噪三件套、门禁全链路、3D 场景本体），拆开会出现「只做去重不做聚类」的半成品状态。执行时按「同一故事、迭代内分两段验收」处理，而不是拆成两个独立故事。

### 2.2 角色卡

角色取自 SRS 3.2，另加一类「系统」——它不是人，但承担定时任务与后台保障，必须显式建模，否则「数据不丢」「按时产出」这类要求会无处安放。

| 角色 | 一句话画像 | 核心诉求 | 验收时最在意什么 | 故事数 |
|---|---|---|---|---|
| **值班员** | 7×24 两人轮班，8 h 盯屏 | 少告警、快定位、操作步数少 | 推送条数、点击次数、确认耗时 | 14 |
| **运维工程师** | 环境与设备组、电气组，每日 2 ~ 3 次 | 规则可自助调、判断权在自己手里 | 规则生效时间、误报条数、证据是否可追 | 11 |
| **管理员** | 系统管理员，每周 1 ~ 2 次 | 合规可审计、权限可控、数据可留可查 | 审计覆盖率、留存期、外发是否脱敏 | 5 |
| **系统（定时任务 / 后台）** | 采集、计算、降噪、护栏等无人值守进程 | 不丢数据、按时产出、故障可自愈 | 丢失条数、时延分位、幂等性 | 4 |

**为什么「系统」也要有故事**：C-14（系统自身不得成为故障源）要求这些能力有明确的责任人与验收口径。写成「作为系统，我需要在断连时缓存数据」并不是拟人化修辞，而是把「不可见的可靠性」变成可排期、可验收的条目。

### 2.3 验收标准写法

统一模板：

```
Given <前置条件：数据状态、配置状态、环境状态>
When  <触发动作：用户操作 / 注入 / 定时到达 / 故障发生>
Then  <可观测结果：条数、时间、比例、状态码，必须含阈值>
```

三条硬规则：

1. **Then 必须可观测**：条数（0 条 / 1 条 / 99 条）、时间（≤ 3 s / P95 ≤ 60 s）、比例（≥ 99% / ≤ 20%）、状态码（400 / 403 / 409）四者至少其一；
2. **一条 Given-When-Then 只验一个判据**，不把「快、准、稳」塞进同一句；
3. **性能判据必须带统计口径**：写「P99 ≤ 3 s」而不是「3 s 内响应」，因为后者既可理解为单次也可理解为均值。

**禁用词表**（出现即退回重写）：流畅、友好、及时、稳定、高效、合理、尽量、适当、优化体验、显著提升。

### 2.4 故事点与节奏

**换算基准**：`1 故事点 ≈ 0.5 人日`。这个比例是相对基准，不是绝对工时——它把「一个熟练的动环运维兼开发者、每周能投入 3.5 人日」作为标尺。

| 点数 | 折算人日 | 典型内容 |
|---|---|---|
| 1 | 0.5 | 单点配置、单个查询语句、一处文案与校验 |
| 2 | 1 | 单条规则类型、单个状态校验 |
| 3 | 1.5 | 单页面加一个接口、单类规则的完整判定 + 验收 |
| 5 | 2.5 | 一个端到端小闭环（配置 → 生效 → 可查） |
| 8 | 4 | 跨 2 ~ 3 个组件的链路（采集 → 入库 → 展示） |
| 13 | 6.5 | 多组件 + 多判据的完整能力（降噪三件套、门禁全链路、3D 场景） |

**产能与迭代口径**：

| 项 | 取值 | 说明 |
|---|---|---|
| 周有效投入 | 3.5 人日 | 业余推进，已扣除会议、值守与中断 |
| 迭代长度 | 4 周 | 与业余节奏匹配，短迭代会导致每个迭代都在做环境准备 |
| 单迭代名义容量 | 14 人日 = 28 点 | 3.5 × 4 |
| 单迭代排产容量 | 24 点 | 名义 28 点扣除约 15% 缓冲（环境故障、需求澄清、返工） |
| 全量故事点 | 215 点 = 107.5 人日 | 34 条故事合计 |
| 折算周期 | 约 31 周纯投入，按 9 个迭代（36 周）排 | 差额即缓冲，见 5.3 |

> **不要把这些数字当承诺**：若实际投入降到 2.5 人日/周，Release 1 需要从 5 个迭代扩到 7 个，而不是砍掉 M 类故事——这是第 7 节裁剪原则的前提。

## 4. 故事详表

### 4.1 M1 采集接入

#### US-01 设备协议接入与适配

**故事**：作为运维工程师，我希望通过配置而不是改代码接入 Modbus TCP / SNMP / MQTT 三类设备，以便新增厂商设备时不必等发版。

**角色** 运维工程师 ｜ **BR** BR-01 ｜ **FR** FR-M1-01 ｜ **优先级** M ｜ **点数** 8（≈4 人日）｜ **迭代** R1-IT1 ｜ **依赖** 无

**验收标准**

1. Given 已备好 3 台模拟设备（三类协议各 1 台）When 在台账中完成协议参数配置并启用采集 Then 30 s 内首帧数据入库，且每条记录含 `device_id`、`point_id`、`value`、`quality`、`ts` 五个字段，缺字段条数 = 0。
2. Given 同一协议下新增 1 台设备 When 只改配置、不改代码 Then 新设备 30 s 内产出数据，采集服务重启次数 = 0，代码变更行数 = 0。
3. Given 两台设备的寄存器地址重复配置 When 保存 Then 保存被拒绝并定位到冲突字段，静默覆盖条数 = 0。
4. Given 一台设备协议参数填写错误（如从站号越界）When 启用采集 Then 该设备状态为「未知」而非「在线」，且错误原因可在设备详情读到。

**备注**：本条只验「接得进」，不验「接得全」；FR-M1-09（协议可插拔）的改造量判据由 NFR-MOD-01 承接，不进本故事的验收。

#### US-02 分频采集与统一时钟

**故事**：作为系统，我需要按变化速率分频采集并统一时间基准，以便快变数据不被慢变设备拖慢、乱序与时钟漂移可控。

**角色** 系统 ｜ **BR** BR-01 ｜ **FR** FR-M1-02、FR-M1-10 ｜ **优先级** M ｜ **点数** 5（≈2.5 人日）｜ **迭代** R1-IT1 ｜ **依赖** US-01

**验收标准**

#### US-31 知识库问答与关键词降级

**故事**：作为运维工程师，我希望用自然语言问手册里的问题并看到出处，以便新人不必翻几百页 PDF 找答案。

**角色** 运维工程师 ｜ **BR** BR-09 ｜ **FR** FR-M6-04、FR-M6-05 ｜ **优先级** S ｜ **点数** 8（≈4 人日）｜ **迭代** R2-IT7 ｜ **依赖** US-32

**验收标准**

1. Given 50 条测试问题 When 逐条提问 Then 答案含正确来源段落 ≥ 70%，来源可点击定位到原文段落。
2. Given 生成内容无检索来源 Then 必须标注「无依据」，抽检 10 条标注 10 条。
3. Given 知识库确实无相关内容 Then 明确回答「知识库无相关内容」，编造答案条数 = 0。
4. Given 停掉向量库 When 提问 10 个常见问题 Then 检索入口仍可用，≤ 3 s 返回片段列表，结果条数 ≥ 1。
5. Given 处于降级状态 Then 界面标注「已降级」（显示率 100%），不把片段列表伪装成生成答案。

**备注**：70% 与「无依据必须标注」是一对约束——只追命中率会鼓励模型胡编，标注机制是安全阀。

#### US-32 送模脱敏与 AI 输出只读护栏

**故事**：作为管理员，我希望外发内容在出门前完成脱敏、AI 结果在类型上就不能作为控制入参，以便引入大模型不突破数据不出内网的底线。

**角色** 管理员 ｜ **BR** BR-09、BR-08 ｜ **FR** FR-M6-07、FR-M6-08 ｜ **优先级** M ｜ **点数** 5（≈2.5 人日）｜ **迭代** R1-IT3 ｜ **依赖** 无（须先于 US-30）

**验收标准**

1. Given 抓包审计 100 条外发请求 Then 真实设备编号、IP、机房位置、人名出现次数均为 0。
2. Given 构造 5 条含敏感信息的请求 Then 5 条全部被脱敏或拦截，原样外发条数 = 0。
3. Given 脱敏规则校验失败或命中黑名单 Then 拒绝外发并记录（构造 3 次，拦截 3 次，记录 3 条）。
4. Given 构造 5 次将 AI 结果作为控制接口入参 Then 5 次均被拒绝（类型校验拦截），控制指令下发条数 = 0。
5. Given 代码审查 When 检索「AI 输出 → 控制接口」调用路径 Then 直连路径数 = 0，审查记录留档。

**备注**：本故事是 M6 其余故事的前置条件——先有护栏再接模型，顺序颠倒会导致 US-30 / US-31 的验收数据本身包含未脱敏外发，无法通过第 1 条。Q-4（模型是否允许走公网）仍为暂定，若被信息安全部否决，本故事的第 4、5 条仍成立，第 1 ~ 3 条转为「全面禁止外发」的实现。

#### US-33 自然语言查询

**故事**：作为运维工程师，我希望用中文问句查出「昨天 A 机房温度最高的三个机柜」这类结果，以便不写查询语句也能做临时分析。

**角色** 运维工程师 ｜ **BR** BR-09 ｜ **FR** FR-M6-06 ｜ **优先级** C ｜ **点数** 5（≈2.5 人日）｜ **迭代** R3-IT8 ｜ **依赖** US-07

**验收标准**

1. Given 30 条标准问句 Then 生成查询可执行率 ≥ 80%，结果与人工构造查询一致率 ≥ 90%。
2. Given 5 条含删除 / 更新意图的问句（构造）Then 5 条 100% 被拒绝，写操作执行条数 = 0。
3. Given 一次成功查询 Then 回显所用查询语句供核对，语句仅含只读语义（SELECT 类），含写关键字条数 = 0。
4. Given 生成语句不可执行 Then 给出可读的失败原因并允许改写，不返回数据库错误堆栈或表结构（泄露字段数 = 0）。

**备注**：C 类，随 Release 3 交付；裁剪时第 1 个被砍（见第 7 节），因为它对 G-1 ~ G-6 均无直接贡献，只是效率增强。

#### US-34 短期趋势预测

**故事**：作为运维工程师，我希望系统对温度、负载率、电池容量给出 30 min 以上的预测，以便在越限前介入而不是等告警。

**角色** 运维工程师 ｜ **BR** BR-12 ｜ **FR** FR-M6-11 ｜ **优先级** C ｜ **点数** 8（≈4 人日）｜ **迭代** R3-IT9 ｜ **依赖** US-07、US-10

**验收标准**

1. Given 24 h 回放数据 When 逐测点预测 Then 提前 ≥ 30 min 命中越限的比例 ≥ 70%，误报率 ≤ 30%。
2. Given 预测结果 Then 附置信区间，与阈值告警并列展示，替代阈值告警条数 = 0。
3. Given 预测服务停止 Then 阈值告警与变化率告警 100% 不受影响（各验证 3 次）。
4. Given 历史样本不足 When 请求预测 Then 标注「样本不足」并不展示预测曲线，以预测值冒充实测值的条数 = 0。

**备注**：SRS 9.2 已注明电池容量预测样本需 ≥ 3 个月，P6 只能用回放数据验证，论文中须标注「样本受限，结论为定性」。

## 6. 与 SRS MoSCoW 的一致性核对

### 6.1 核对结论

| 核对项 | 结论 | 说明 |
|---|---|---|
| M 级 FR 是否都被 M 故事覆盖 | 基本覆盖（35/40） | 5 条未切片，见 6.4，均为非功能承接或否定型需求 |
| S 级 FR 是否被 M 故事「偷渡」 | 有 3 条，已裁决 | 见 6.3 的 C-1、C-2，均在故事备注中写明「先交付最小可用、后补完备度」 |
| C 级 FR 是否被塞进 M/S 故事 | 无 | 6 条 C 级 FR 与 6 个 C 故事一一对应 |
| 故事级 M 数（18）与 FR 级 M 数（40）是否矛盾 | 不矛盾 | 一个故事平均覆盖 1.6 条 FR，数量比不可直接比较 |
| 是否有「故事是 S、内含 M」的情况 | 无 | 优先级取所含 FR 的最高级，规则见 6.2 |

### 6.2 裁决规则（先定规则，再判个案）

1. **规则 A（就高不就低）**：故事优先级 = 所含 FR 的最高优先级。防止「挂 S 的名、藏 M 的活」导致排期失真。
2. **规则 B（同故事内可降完备度，不可降能力）**：M 故事里夹带的 S 级 FR，允许「先交付能跑通的最小实现，完备度在下一批次补齐」，但必须在故事的「备注」里写明哪条判据属于后补项。
3. **规则 C（C 级不得混入 M/S）**：C 级 FR 一律单独成故事，随 Release 3 整体裁剪；若某 C 能力被 M 故事变相依赖，说明故事切错了，须重切。
4. **规则 D（否定型需求不切片）**：如 FR-M4-08（不提供空调远程调节），本身没有用户价值切片，进验收清单而非故事清单。

## 论文可引用段落

> 本段适用于「敏捷开发」「需求管理」「范围管理」类论文的需求切片与排期部分。
>
> 需求规格定稿后，我没有直接进入设计，而是把 69 条功能需求切成 34 个用户故事。切片依据不是模块，而是「谁为了什么要用」：同属告警，「值班员确认一条告警」以操作步数验收，「系统在抑制窗口内去重」以推送条数验收，交付节奏不同，硬塞进一个任务只会让验收失焦。每个故事用 INVEST 校验，验收标准统一写成 Given-When-Then 并带阈值，例如「注入 100 条同源告警，推送 1 条、抑制计数 99」。项目由在职人员业余推进、每周有效投入约 3.5 人日，因此我用故事点而非人日估算，1 点折算 0.5 人日，按 4 周迭代、名义 28 点并留 15% 缓冲排产。34 个故事共 215 点，分三个发布：18 个必做故事构成采集到定位的闭环，Release 2 补效率与合规，Release 3 才是 3D 与预测。裁剪顺序事先定死——先砍 C、再砍 S、M 不砍。范围控制由此不再是告急时的临时妥协，而是一条事先约定的规则。
