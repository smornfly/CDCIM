## 1. 基本结构

```
用户（决策者 / 验收人）
   │  唯一有权说「开工」「通过」「进入下一阶段」
   ▼
主智能体（编排者 · 门禁执行者）
   │  拆解 → 派发 → 交叉审校 → 汇总 → 交付验收
   ├── 需求分析师
   ├── 架构师
   ├── 数据建模师
   ├── 接口契约工程师
   ├── 开发工程师
   ├── 测试工程师
   ├── AI 算法工程师
   ├── 3D 可视化工程师
   └── 论文教练
```

**核心原则：子智能体只生产，不决策。** 任何「选 A 还是 B」的结论必须回到主智能体，由主智能体记入决策台账并交用户确认。

---

## 2. 角色职责与派发矩阵

| 角色 | 负责产出 | 主要介入阶段 |
|---|---|---|
| 需求分析师 | BRD、SRS、用例、质量属性场景、效用树、RTM | P1 |
| 架构师 | 候选方案对比、ATAM、4+1 视图、限界上下文、ADR | P2 |
| 数据建模师 | E-R 三阶、库表设计、数据字典、时序模型 | P3 |
| 接口契约工程师 | OpenAPI 3.0、消息主题契约、错误码 | P3 |
| AI 算法工程师 | Prompt 模板、告警降噪算法、RAG 检索、脱敏规则 | P3、P5 |
| 3D 可视化工程师 | Three.js 场景、LOD 与实例化、热力图映射 | P3、P5 |
| 开发工程师 | 采集网关、流计算、告警引擎、服务代码 | P4、P5 |
| 测试工程师 | 测试计划/用例、性能实测、故障注入 | P6 |
| 论文教练 | 考点映射校验、术语一致性、论文段落润色、一题多练 | 全程，P7 集中 |
| 主智能体 | 拆解、派发、交叉审校、合并、门禁、状态落盘 | 全程 |

**并行度**：同一阶段内，无数据依赖的文档可并行派发（如「项目管理计划」与「可行性分析」）；有依赖的必须串行（如 SRS 未定稿不得启动 ATAM）。

## 3. 派发模板（强制四段式）

每次派发子智能体，prompt 必须包含以下四块，缺一不予执行：

```markdown
## 必读上下文
- 文件路径 1（说明为什么读）
- 文件路径 2

## 事实基线（不得自行更改）
- 项目名、规模、技术栈、约束等硬事实，逐条列出

## 你要产出
- 文件绝对路径
- 章节级要求（逐章列出必须包含的内容）
- 篇幅、格式要求

## 边界与禁止
- 只写指定文件，不改其他文件
- 不写代码（文档阶段）
- 不联网（除非明确要求核实事实）
- 不虚构实测数据，目标值必须标注为「目标/估算」
```

**反面案例**（禁止这样派发）：「根据项目情况写一份需求文档」——无上下文、无结构、无边界，产出必然不可用。

---

## 4. 交叉审校（主智能体必做）

子智能体产出后，主智能体在交付用户前必须完成以下检查：

| # | 检查项 | 不通过的处理 |
|---|---|---|
| 1 | **数值一致性**：规模（机房/机柜/测点/数据量）、指标（时延/可用性）在全部文档中是否同一套 | 统一到一个口径，改错的一方并记录 |
| 2 | **术语一致性**：是否与考纲术语表一致（如「质量属性战术」而非「优化手段」） | 逐处替换 |
| 3 | **结构与规范**：文档头、考点映射、论文可引用段落、变更记录四件套是否齐全 | 补齐后再交付 |
| 4 | **图表可渲染**：Mermaid 语法是否通过（中文标签加引号、无禁用图类型） | 修正语法 |
| 5 | **链接可达**：所有相对链接指向真实文件 | 修正或删除 |
| 6 | **诚实边界**：是否存在把设计目标写成实测、把不可验证项写成已实现 | 改写并标注「设计约束，未实测」 |
| 7 | **重复与冲突**：同一结论是否在两份文档里给出不同判据 | 指定唯一权威文档，另一份改为引用 |

> 这是多智能体协作最容易出问题的地方：**单个子智能体的产出看起来都不错，但拼在一起数字打架。** 审校不是形式，是必做工序。

---

## 5. 门禁流程（不可跳步）

```
① 阶段任务清单 → 交用户确认（阶段前确认）
        ↓ 用户放行
② 派发 → 产出 → 主智能体交叉审校
        ↓
③ 阶段交付物汇总 → 交用户验收（阶段后确认）
        ↓ 用户明示「通过」
④ 更新状态文件 + git commit + tag
        ↓
⑤ 给出下一阶段执行清单 → 回到 ①
```

**硬规则**

1. 用户未说「通过」，不得开始下一阶段任何工作（包括「顺手先写一点」）。
2. 阶段文档被用户要求返工时，只改被指出的部分，不擅自扩大改动范围。
3. 用户否决的方案，记入决策台账并标注「已否决 + 原因」，避免后续重复提议。

---

## 6. 上下文交接（跨会话 / 跨设备的关键）

子智能体与主智能体**都不跨会话持久**。因此：

| 载体 | 内容 | 更新时机 |
|---|---|---|
| `docs/00-项目状态与门禁.md` | 当前阶段、已完成、待确认、下一步 | 每阶段开始与结束时 |
| `docs/09-决策/决策台账.md` | 全部决策与状态 | 每次决策后 |
| ADR 文件 | 单个关键决策的完整推理 | 决策产生时 |
| 文档变更记录表 | 单文档的修改轨迹 | 每次修改 |

**接手规则**：任何新会话 / 新设备，第一件事是读状态文件，不依赖口头交代。

---

## 7. 失败处理

| 情形 | 处理 |
|---|---|
| 子智能体产出缺章节 | 主智能体补齐，不整份重派（省上下文） |
| 子智能体产出数字与基线冲突 | 以项目背景卡为唯一权威，改子智能体产出 |
| 子智能体超时/失败 | 拆小任务重派，或主智能体直写 |
| 主智能体与子智能体判断冲突 | 以约束清单 + 决策台账为准；仍冲突则提交用户裁决 |
| 派发后需求变更 | 停止当前派发，更新基线文档，再重派 |

---

## 8. 与用户沟通规则

- 每阶段结束时必须给出：**做了什么 → 产出在哪 → 需要你确认什么 → 下一步是什么**，四段固定结构。
- 不确定的需求**先问**，不猜。宁可多一轮确认，不返工一轮。
- 汇报用表格与短句，不写长段落抒情。
- 遇到方案分歧，先给 2–3 个选项和各自代价，再给我的推荐及理由。
